virtual-bank-agent 설계 기획서

기본 설계 원칙  [원본]
- supervisor 패턴으로 각 Agent로 나누어서 노드 및 그래프를 구현한다.
- subgraph를 이용하여 각 Agent안에 노드 및 그래프를 invoke 하여 supervisor 그래프에 넣는다.
- 이체 및 개인정보 변경 같은 민감정보, 돈과 관련된 사항에는 Human in the Loop를 통하여 승인을 받고 실행한다.
- 공통 부분은 agent를 적용하지 않고 공통 노드로 만든다.

--------------------------------------------------------------------
기본 설계 원칙  [수정]

- supervisor 패턴으로 도메인별 Agent를 나누어 노드 및 그래프를 구현한다.

- 각 Agent는 compile한 subgraph를 supervisor 그래프의 "노드로 직접 등록"한다.
  (builder.add_node("transfer", transfer_graph))
  하위 에이전트로 넘길 때 tool 호출로 감싸지 않는다.
  이유: interrupt()로 멈췄다가 재개하면, 멈춘 그 줄부터 이어지는 것이 아니라
        "그 노드를 처음부터 다시 실행"한다. (Python의 input()과 다름)
        즉 재개 단위 = 노드 하나.
        tool 안에 감싸면 재실행 범위가 tool 함수 전체로 커져서
        interrupt 앞에 있던 코드(기록 남기기, 잔액 차감 등)가 두 번 실행된다.
        LLM이 tool을 여러 개 동시에 호출한 경우, 하나가 멈추면
        같은 노드의 나머지 tool도 전부 다시 실행된다.
        subgraph를 노드로 등록하면 재실행 범위가 그 안의 작은 노드 하나로 줄어든다.
  * state 자체는 checkpointer가 저장하므로 잃어버리지 않는다.
    문제는 "기억"이 아니라 "재실행 범위"다.

- interrupt()가 있는 노드에는 부작용(저장, 기록, 잔액 변경)을 두지 않는다.
  계산 / 승인 / 실행을 노드 3개로 쪼갠다.
      propose_node : 처리안 계산만. 저장 안 함
      approve_node : interrupt() 한 줄만. 다른 일 안 함
      execute_node : 승인된 뒤에만 실제 저장
  이유: approve_node가 통째로 재실행되어도 interrupt() 한 줄뿐이라 피해가 없다.
        승인을 각 Agent 안에 두지 않고 공통 노드로 빼는 진짜 이유도 이것이다.
        부작용 없는 승인 노드 하나를 모든 업무가 공유한다.

- JSON에 쓰기(저장)가 일어나는 모든 업무는 HITL 승인을 받고 실행한다.
  읽기만 하는 조회는 승인 없이 바로 처리한다.
  이유: "민감정보/돈"은 매번 사람이 판단해야 해서 기준이 흔들린다.
        (카드 분실정지는 돈이 안 움직이고, 계좌 별명 변경은 민감정보가 아니지만 둘 다 승인 대상)
        "파일을 바꾸느냐"는 기계적으로 갈리므로 기능이 늘어도 헷갈리지 않는다.

- 공통 부분(승인, 맥락 확인, 부족 정보 질문, 오류/복구, 결과 저장)은
  agent가 아니라 공통 노드로 만든다.
  공통 노드는 supervisor의 라우팅 대상에 포함하지 않는다.
  이유: 사용자가 "승인 업무 해줘"라고 요청하지 않는다.
        공통은 목적지가 아니라 계좌/카드 업무 흐름 중간에 끼어드는 단계다.

- 처리의 성공/실패 여부와 금액·잔액 등 수치는 Python 함수가 낸 값을 그대로 사용한다.
  LLM은 그 값을 넣어 문장을 다듬는 역할만 하며,
  성공 여부를 판단하거나 수치를 다시 만들어내지 않는다.


흐름  [원본]
입력(자연어) -> Virtual_Bank_Supervisor_Agent -> 각 supervisorAgent(계좌, 카드, 공통) -> 맞는 기능 실행 -> 결과 반환 -> Virtual_Bank_Supervisor_Agent에서 최종 검토(llm이 보기 좋은 말로) 후 출력
* 각 기능별 공통 노드를 두어 승인, 맥락확인, 사용자 확인, 오류, 복구 등을 담당한다.

* 되돌아오는 경로 정리 (원본에 빠져 있던 부분)
  - 정보 부족   : 질문 -> 답변 -> 같은 지점으로 복귀 (분기 1 루프)
  - 승인 대기   : interrupt -> 다음 입력 -> 분기 0 -> 멈춘 자리에서 resume
  - 거절        : 실행/저장을 타지 않고 종료
  - 승인 전 수정: 처리안 갱신 -> 승인 요청으로 되돌아감

* 승인 이후 실행 직전에 전제(잔액 등)가 바뀌어 처리 내용이 달라지면
  그대로 실행하지 않고 다시 승인받거나 재요청을 안내한다.

* 공통 노드(승인, 맥락 확인, 부족 정보 질문, 오류/복구, 저장)는
  supervisor가 고르는 목적지가 아니라 위 흐름 중간에 끼어드는 단계다.

1. 계좌  [수정]

■ 오타
  AcoountAgent -> AccountAgent,  acoount_router -> account_router
  이체 에약 -> 이체 예약
  check_missing_information 은 "확인"이 아니라 "질문하기"다 -> ask_missing_information


■ 이 블록 전체에 걸린 문제

 (1) 계층 분류(3단 라우팅)는 그대로 간다.  ** 의도된 설계 **
     Supervisor(계좌/카드) -> AccountAgent(이체/조회/설정) -> TransferAgent(즉시/조건부/나눔)
     이유: 각 층의 선택지를 3~4개로 줄여야 그 층이 자기 도메인 안에서 정확히 판단한다.
           층마다 도메인 프롬프트를 따로 쓸 수 있고,
           카드 기능을 추가해도 계좌 쪽 프롬프트를 건드리지 않는다.
     -> 다만 이 구조를 쓰려면 아래 3가지를 반드시 채워야 한다.

   (1-a) 오분류 반송 경로가 없다.   ** 계층 분류를 쓰는 이상 필수 **
         1단계가 "계좌"로 잘못 보내면 카드 기능에는 영영 도달하지 못한다.
         하위 Agent가 "내 도메인이 아님"을 반환해 Supervisor로 되돌리는 경로를 둔다.
             AccountAgent -> (해당 없음) -> Supervisor 재분류
             재분류도 실패하면 -> 불가 안내
         되돌린 횟수를 state에 세어 무한 왕복을 막는다 (예: 1회까지만 재분류).

   (1-b) 각 라우터의 선택지와 판단 기준이 적혀 있지 않다.
         지금은 세 곳 모두 "요청 분류(분기)" 한 줄뿐이다.
         층을 나눈 목적이 "각 층이 자기 도메인에서 정확히 판단"하는 것인데,
         무엇을 보고 고르는지가 없으면 프롬프트를 쓸 수 없다.
         층마다 아래를 명시한다.
             account_router   : 이체 / 조회 / 설정
                 이체 - 돈을 옮기는 표현(옮겨, 보내, 이체, 송금)
                 조회 - 보여줘, 얼마, 내역, 목록
                 설정 - 이름·별명을 바꾸는 표현
             transfer_router  : 즉시 / 조건부 / 나눔
                 즉시   - 금액이 직접 주어짐            "10만원 옮겨줘"
                 조건부 - "남기고", "빼고" 등 잔액 기준  "40만원 남기고 나머지"
                 나눔   - 입금 대상이 2개 이상           "저축 20만, 여행 10만"
             query_router     : 계좌목록 / 총액 / 거래내역

   (1-c) "필요 정보 확인"이 잘못된 층에 있다.   ** 실제 결함 **
         AccountAgent에 check_information이 있는데,
         그 시점에는 아직 "이체"까지만 정해졌고 이체 유형을 모른다.
         유형마다 필요한 정보가 다르므로 무엇이 부족한지 판단할 수 없다.
             즉시   : 출금계좌 / 입금계좌 / 금액
             조건부 : 출금계좌 / 입금계좌 / 남길 금액
             나눔   : 출금계좌 / 입금계좌별 금액 리스트
         -> 필요 정보 확인과 부족 정보 질문은 transfer_router가 유형을 정한 뒤,
            즉 TransferAgent 층으로 내린다. AccountAgent에는 남기지 않는다.
         조회·설정도 같다. 종류가 정해진 뒤에 필요 정보를 따진다.

     * AccountAgent에 남는 역할 : 요청 분류 / 하위 Agent로 라우팅 / 도메인 밖이면 반송
       (필요 정보 확인, 부족 정보 질문은 내려보냄)

 (2) "정보 전달(tool 사용 -> 각 에이전트)"
     tool로 감싸지 않는다. 위 기본 설계 원칙의 재실행 범위 항목 참고.

 (3) 계좌를 무엇으로 식별할지가 정해져 있지 않다.  ** 실제로 가장 자주 터질 부분 **
     별명은 유일하지 않다.
         생활비 = acc-001(user-001), acc-004(user-002)
         저축   = acc-002(user-001), acc-005(user-003)
     "생활비에서 저축으로 옮겨줘" -> 후보가 각각 2개다.
     별명 -> account_id 해소 함수가 필요하고, 세 기능이 모두 쓰므로 공통 노드에 둔다.
         후보 0개    -> 불가 안내
         후보 1개    -> 확정
         후보 2개 이상 -> 목록 제시 후 사용자 선택
     state에는 별명이 아니라 해소가 끝난 account_id를 담는다.

 (4) "본인 확인"이 세 Agent state에 똑같이 들어 있다.
     인증 자체는 만든다(위 결정 (다) 참고). 문제는 "세 군데에 흩어져 있다"는 것이다.
     -> 인증 노드는 공통에 하나만 둔다. 각 Agent는 인증 결과만 받아서 쓴다.
     -> 각 Agent state에서 "본인 확인" 필드는 지우고,
        공통 state의 "인증 완료 여부 / 인증 시각"을 참조한다.

 (5) 각 Agent의 "승인 요청", "결과 반환"은 공통 노드로 올린다.
     승인을 Agent마다 따로 두면 원칙(부작용 없는 승인 노드 하나를 공유)과 어긋난다.


■ 구조

  Supervisor                      1단 분류 : 계좌 / 카드 / (청구서)
    +- AccountAgent               2단 분류 : 이체 / 조회 / 설정
    |    |                        도메인 밖이면 Supervisor로 반송
    |    +- 이체  TransferAgent    3단 분류 : 즉시 / 조건부 / 나눔
    |    |                             + 필요 정보 확인 / 부족 정보 질문  <- 이 층에서 한다
    |    +- 조회  AccountQueryAgent 3단 분류 : 계좌목록 / 총액 / 거래내역
    |    |                             + 필요 정보 확인 / 부족 정보 질문
    |    +- 설정  AccountSettingAgent
    +- (카드 / 청구서)

  * 3단까지 나누는 이유: 각 층의 선택지를 3~4개로 줄여 그 층이 정확히 판단하게 한다.
  * 필요 정보 확인은 3단(종류가 확정된 뒤)에서 한다. 2단에서는 무엇이 부족한지 알 수 없다.

  공통 노드 : 계좌 해소 / 부족 정보 질문 / 처리안 제시 / 승인 / 저장 /
              오류·복구 / requests 기록 / 결과 문장 정리


■ 이체의 축은 서로 다른 차원이다        <- 원본 기능을 정리하는 방법

  원본의 축(타인 / 본인 / 같은·다른 금융 / 예약)과
  "즉시 / 조건부 / 나눔"은 경쟁하는 목록이 아니라 서로 다른 차원이다.
  한 요청이 네 축 모두에 값을 가진다.

      유형 : 즉시 / 조건부 / 나눔     <- transfer_router가 고른다 (3단 분류)
      대상 : 본인 / 타인              <- 슬롯 값 (입금 계좌 소유자로 판정)
      은행 : 자행 / 타행              <- 슬롯 값
      시점 : 즉시 / 예약              <- 슬롯 값

  예) "타인 계좌로 40만원 남기고 나머지를 내일 보내줘"
      = 유형 조건부 / 대상 타인 / 은행 자행 / 시점 예약

  -> transfer_router는 "유형"만 고르고, 나머지 셋은 정보 추출 단계에서 채운다.
     축마다 추가 검증이 따라붙는다.
         대상 타인 -> 예금주 확인 단계 추가
         은행 타행 -> 은행 선택 + 수수료(넣는다면)
         시점 예약 -> 예약 일시 검증 (과거 시각 불가)

  * 원본처럼 네 개를 한 줄에 나열하면 router가 무엇을 고르는지 흐려진다.
    "유형"만 분류하고 나머지는 슬롯으로 두면 분기가 깔끔해진다.


■ 결정된 것

  (가) 타행 이체의 상대 계좌  ->  등록해서 저장한다
       계좌를 등록·저장할 때 은행명을 함께 입력받는다.
       우리 은행 계좌든 타행 계좌든 같은 방식으로 다룬다.
           등록 시 받는 정보 : 은행명 / 계좌번호 / 예금주 / 별명(선택)
       한 번 등록해 두면 다음부터 별명으로 부를 수 있다.
       -> 계좌 등록 / 조회 / 삭제 기능이 필요하다 (AccountSettingAgent 참고)
       -> 미등록 계좌로 바로 보내는 경우도 허용할지는 구현하면서 정한다

  (나) 예약 이체  ->  예약한 시각에 실제로 이체되게 한다
       예약 목록을 따로 두고, 시각이 되면 처리한다.
           프로그램이 켜져 있는 동안 : 입력을 받을 때마다 지난 예약이 있는지 확인해 처리
           프로그램이 꺼져 있었으면   : 다음 시작 시 지난 예약을 확인해 처리
       예약 항목
           schedule_id / 출금 계좌 / 입금 계좌 / 금액 /
           예약 일시 / status(예약 / 완료 / 취소 / 실패)
       실행 시점 규칙
           등록할 때 승인을 받는다.
           실행 시점에 잔액이 부족하면 실행하지 않고 실패로 남긴다.
           실행 시점에 처리 내용이 달라지면(잔액 부족 등) 자동 실행하지 않고 안내한다.
       -> 예약 조회 / 취소 기능도 같이 만든다

  (다) 본인 확인  ->  기본 인증 단계를 둔다
       민감한 업무(이체, 설정 변경) 전에 인증을 한 번 받는다.
       수단은 아래 중 하나로 정한다 (구현하면서 확정)
           계좌 비밀번호 / 간편 비밀번호(PIN) / 휴대전화번호 / 주민번호 뒷자리
       -> 인증 함수는 각 Agent에 두지 않고 공통 노드에 둔다.
          업무마다 인증 규칙이 갈리면 관리가 안 된다.
       -> 인증 시점은 "처리안 제시 전"에 둔다.
          승인 직후에 두면 인증이 틀렸을 때 처리안을 다시 만들어야 해서 흐름이 꼬인다.
       -> 인증 유효 기간 : 세션 단위.  [결정됨]
          한 번 인증하면 프로그램을 끌 때까지 유효하다. 업무마다 다시 받지 않는다.
          세션 = thread_id 하나. 재시작하면 풀리고 복구 시점에 다시 받는다.


■ 이 항목들은 유지한다 (구조 문제이지 기능 문제가 아님)

  각 Agent의 "승인 요청"   -> 공통 노드로 이동
  각 Agent의 "결과 반환"   -> Supervisor 최종 정리와 중복
  state의 "본인 확인"      -> 전역 설정으로 이동

* 이체 : TransferAgent  [수정]

** 기능
  [유형]  transfer_router가 고르는 3단 분류
- 즉시이체              출금계좌 + 입금계좌 + 금액
- 조건부 이체           "40만원 남기고 나머지" -> 이체액 = 잔액 - 남길 금액
- 여러 계좌로 나눠 이체  입금계좌별 금액 + 총액

  [축]  유형과 별개로 함께 붙는 값. 위 "이체의 축" 항목 참고
- 본인 / 타인 이체
- 자행 / 타행 이체
- 즉시 / 예약 이체

** state
- 출금 계좌 ID          별명이 아니라 해소가 끝난 account_id
- 입금 계좌 목록        [{account_id 또는 외부계좌, 금액}, ...]
                        * 나눠 이체까지 같은 구조로 담기 위해 처음부터 리스트로 둔다
- 이체 유형             즉시 / 조건부 / 나눔
- 남길 금액             조건부일 때만. 0 이상 정수
- 총 이체액
- 대상 구분             본인 / 타인
- 은행 구분             자행 / 타행
- 받는 은행             타행일 때
- 예금주 이름           타인·타행일 때 확인용
- 비밀번호              입력값. state에 남기지 않고 검증 후 즉시 버린다
- 예약 일시             예약일 때
- 잔액 스냅샷           처리안을 만든 시점의 출금계좌 잔액
                        * 진실은 저장된 데이터다. 승인 대기 중에 잔액이 바뀔 수 있으므로
                          실행 직전에 다시 읽어 비교하는 용도로만 쓴다
- 처리안(proposal)      사용자에게 보여주고 승인받을 확정 내용
- 승인 상태             대기 / 승인 / 거절
- 요청 ID               처리 기록에 남길 식별자
- 실패 사유

  * 원본 state에는 승인 관련 항목이 하나도 없었다. 이체의 핵심이 HITL인데도.
  * 비밀번호는 승인 대기 중에 계속 들고 있지 않는다. 검증 직후 지운다.

** 필요 함수
- 계좌 해소                          (공통) 별명 -> account_id
- 이체 유형 분류(transfer_router)    즉시 / 조건부 / 나눔
- 계좌 확인(transfer_account_verification)
      출금·입금 계좌 존재 확인
      타인·타행이면 예금주 이름 확인 단계 추가
- 비밀번호 확인(transfer_check_password)
      * 처리안 제시 전에 둔다. 승인 직후에 두면 틀렸을 때
        처리안을 다시 만들어야 해서 흐름이 꼬인다
- 이체액 계산(transfer_calculate_amount)
      즉시   : 입력 금액 그대로
      조건부 : 잔액 - 남길 금액
      나눔   : 계좌별 금액 합산
- 예약 검증(transfer_check_reservation)
      예약 일시가 과거이면 불가
      예약 목록에 등록하고, 실행 시점 처리 방식은 위 "결정해야 할 것 (나)" 참고
- 검증(transfer_validate)            -> 불가 분기
      이체액 0 이하
      원 단위 정수가 아님
      출금계좌 잔액 < 총액
      출금계좌 == 입금계좌
      타행인데 은행 미지정
- 처리안 생성(transfer_build_proposal)      * 계산만. 저장 없음
- 승인                               (공통 노드. interrupt() 한 줄만)
- 실행 직전 재검증(transfer_revalidate)     <- 원본에 없던 것
      승인 시점과 잔액이 달라져 이체액이 바뀌면 그대로 실행하지 않고
      다시 승인받거나 재요청을 안내한다
- 이체 실행(transfer_execute)
      출금계좌 잔액 차감 / 입금계좌 잔액 증가
      거래 내역에 출금 1건 + 입금 1건 기록     <- 원본에 빠져 있던 부분.
          빠지면 이후 "이번 달 출금 내역" 조회 결과가 틀어진다
      나눠 이체는 전체를 한 번에 반영한다. 일부만 반영하지 않는다 (전부 아니면 전무)
- 저장                               (공통) 실패 시 이체 전 상태 유지
- 처리 기록                          (공통) "아까 이체 됐어?" 후속 조회의 근거

* 조회 : AccountQueryAgent  [수정]

** 기능   (원본 "날짜 조회 / 검색어 조회" 2개 -> 아래 3개)

      거래 데이터가 2026-08-28 ~ 2026-09-20 에만 있다.
      실제 오늘 날짜로 "이번 달"을 계산하면 아무것도 나오지 않는다.
      기준일을 상수로 고정한다 (예: 2026-09-22)
      이번 달 = 기준일이 속한 달
      이번 주 = 월요일 ~ 일요일
      기간은 시작일과 종료일을 포함한다
- 계좌 목록 조회(query_accounts)
- 잔액 합산(query_total_balance)
- 거래 내역 조회(query_transactions)
      * 원본처럼 키워드검색 / 날짜검색으로 함수를 쪼개지 않는다.
        실제 요청은 조건 조합이기 때문이다.
        "5만원 이상 결제한 내역" = 금액 + 유형 필터인데
        원본에는 금액 필터가 아예 없었다.
      필터 : 기간 / 금액 / 유형 / 검색어
      정렬 : occurred_at 내림차순
      카드 거래면 card_id로 카드 이름을 찾아 붙인다

* 조회는 파일을 바꾸지 않으므로 승인(HITL) 없이 바로 출력한다.

- 비밀번호 변경
- 분실 신고/ 재발급 
- 별칭 변경

--------------------------------------------------------------------
2. 카드  [수정]

■ 오타
  card_setting_regester -> card_setting_register
  맴버십 -> 멤버십


■ 구조 — 2단 분류에 자리가 부족하다

  원본 2단 : 조회/결제 + 설정 = 2개
  실제로는 성격이 다른 덩어리가 4개다.

  Supervisor
    +- CardAgent                   2단 분류 : 조회 / 결제 / 설정 / 재발급
    |    |                         도메인 밖이면 Supervisor로 반송
    |    +- 조회    CardQueryAgent
    |    |            3단 : 은행별 카드조회 / 결제계좌 / 실카드번호 / 멤버십 / 이용내역
    |    +- 결제    CardBillingAgent
    |    |            3단 : 요금조회 / 명세서 / 전체결제 / 분할결제
    |    +- 설정    CardSettingAgent
    |    |            3단 : 등록·해지 / 비밀번호변경 / 분실·신고 / 잠금·해제 / 별칭변경
    |    +- 재발급  CardReissueAgent
    |                 3단 : 신청 / 신청조회 / 배송지수정 / 신청취소
    |
    |    * 각 3단에서 필요 정보 확인 / 부족 정보 질문을 한다

  왜 조회와 결제를 나누는가
      조회는 읽기만 한다. 승인이 필요 없다.
      결제는 돈이 나간다. 승인이 필요하다.
      원본은 둘을 CardCheckAgent 하나에 묶어서 승인 지점이 흐려졌다.

  왜 재발급을 따로 빼는가
      신청 / 조회 / 수정 / 취소가 딸린 독립 업무이고,
      "신청 상태에 따라 수정 가능 여부가 갈리는" 규칙이 상태 변경과 완전히 다르다.


■ 이 블록에서 채워야 할 것

 (1) CardAgent(2단) — 계좌와 같은 세 가지
     - "조회/결제 정보 전달(tool 사용)" : tool로 감싸지 않는다
     - "필요 정보 확인 / 부족한 정보 질문" : 3단으로 내린다
       설정 유형마다 필요 정보가 달라서 2단에서는 무엇이 부족한지 알 수 없다
           등록      : 카드 종류 / 연결 계좌 / 카드 이름
           비밀번호  : 현재 비밀번호 / 새 비밀번호
           잠금      : 대상 카드만
     - 도메인 밖이면 Supervisor로 반송

 (2) 승인이 하나도 없다.   ** 이 블록에서 제일 큰 구멍 **
     등록 / 해지 / 비밀번호 변경 / 분실 / 신고 / 잠금 / 해제 / 별칭 변경 /
     재발급 신청·수정·취소 / 요금 결제 / 분할 결제
     -- 전부 데이터를 바꾼다. 원칙에 따라 전부 승인 대상이다.
     원본 CardSettingAgent 함수 목록에는 승인이 한 줄도 없다.

 (3) 카드 조회 항목에 "상태"가 빠져 있다.
     정지·잠금 기능을 만들어 놓고 조회에서 상태를 안 보여주면
     사용자가 결과를 확인할 방법이 없다.

 (4) 카드 식별 기준이 없다.
     "그 카드 잠가줘", "생활비 카드" 같은 표현을 card_id로 바꾸는 단계가 필요하다.
     소유자로 먼저 거른 뒤 이름을 맞춘다.
         후보 0개 -> 불가 안내
         후보 1개 -> 확정
         후보 2개 이상 -> 목록 제시 후 선택
     지시 표현("그 카드")은 직전 대화의 대상을 확인하고,
     확신할 수 없으면 되묻는다. (공통 노드)

 (5) state "조회/결제 할 계좌"는 대상이 틀렸다.
     카드 업무의 대상은 카드다. 결제 계좌는 별도 슬롯이다.
     "본인 확인"은 계좌와 같은 이유로 전역 설정으로 뺀다.

 (6) "분실 / 신고"  ->  하나로 합친다.  [결정됨]
     사용자가 "잃어버렸어", "카드 없어졌어" 라고 자연어로 말하면
     그 카드 상태를 "분실 및 정지"로 바꾼다.
     분실 / 도난 / 부정사용을 각각 다른 상태로 나누지 않는다.
     결과가 모두 "카드를 못 쓰게 만든다"로 같기 때문이다.
         status        -> lost   (분실 및 정지)
         report_reason -> 분실 / 도난 / 부정사용   * 기록만 남기고 처리는 동일
     원본의 "분실 / 신고 / 재발급" 3분기는
         분실·신고 = 상태 변경 (CardSettingAgent)
         재발급     = 별도 업무 (CardReissueAgent)
     로 나뉜다.


■ 카드 상태 정의와 전이표      <- 원본에 없던 것. 카드 업무의 핵심 분기 조건

  status 값 (안)
      active     사용 가능 (초기값)
      locked     일시 잠금
      lost       분실 / 신고 정지     (사유는 report_reason에 따로)
      cancelled  해지됨

  전이표
      active    --일시잠금--> locked
      active    --분실·신고--> lost
      active    --해지------> cancelled
      locked    --잠금해제--> active
      locked    --분실·신고--> lost      사용가능/일시잠금 카드 모두 정지 가능
      locked    --해지------> cancelled
      lost      --잠금해제--> 불가       ** 분실 정지는 해제로 되돌릴 수 없다 **
      lost      --일시잠금--> 불가
      lost      --재발급----> 신청 가능
      cancelled --무엇이든--> 불가
      이미 같은 상태 -> 불가 안내 (이미 잠긴 카드를 또 잠그기 등)

  * 일시 잠금과 분실 정지를 구분한다. 잠금은 계좌 잔액과 기존 거래를 건드리지 않는다.
  * 해지는 카드를 목록에서 지우지 않고 cancelled로 둔다.
    지우면 그 카드로 발생한 이용 내역이 참조를 잃는다.


■ 재발급 신청의 상태 설계      <- 원본에 없던 것

      status
          received   접수     - 배송지 수정 / 취소 가능
          making     제작중   - 수정·취소 불가
          shipping   배송중   - 수정·취소 불가
          cancelled  취소됨

  * 제작중 / 배송중 상태는 테스트 데이터로 미리 만들어두고
    수정·취소가 막히는지 확인한다.
  * 실제 제작·배송을 진행하는 기능은 만들지 않는다.

* 결제 : CardBillingAgent  [수정]
  (원본 CardCheckAgent에서 결제 부분을 떼어냄. 승인이 붙는 쓰기 업무이기 때문)

** 기능
- 요금 조회        청구 월 / 청구 총액 / 결제일 / 납부 상태
- 명세서 조회      해당 청구에 포함된 거래 목록
- 요금 결제(전체)  청구 총액 전액 결제
- 부분 결제        금액을 지정해 일부만 결제      <- 청구서 카테고리에서 옮겨옴
- 분할 결제(할부)  개월 수를 정하고 회차별로 결제
- 일괄 결제        카드 여러 장의 요금을 한 번에  <- 청구서 카테고리에서 옮겨옴

** 결제 방식 4가지의 차이     ** 헷갈리기 쉬운 지점 **
      전체 : 청구 총액을 전부 낸다
      부분 : 지금 일부만 낸다. 남은 금액만 줄어든다. 회차는 생기지 않는다
      분할 : 앞으로 N개월에 걸쳐 나눠 낸다. 미래 회차가 생긴다
      일괄 : 카드 여러 장의 청구를 한 번에 처리한다
      * 부분과 분할은 다른 개념이다. 부분은 "지금 얼마만", 분할은 "앞으로 몇 번에"

** 저장 규칙
      전체 / 부분 / 분할 : 잔액 차감 + 거래 기록 + 청구 상태를 한 번에 저장한다.
                           하나라도 실패하면 전부 되돌린다
      일괄               : 건별로 처리하고 건별로 저장한다.
                           2건째가 실패해도 1건째 결제는 유지한다
                           잔액 부족인 건은 건너뛰고 다음 건을 확인한다
                           결과를 완료 / 실패 / 미처리로 나누어 안내한다
                           승인은 전체에 대해 한 번만 받는다
      * 나눠 이체는 전부 아니면 전무, 일괄 결제는 건별 확정이다. 규칙이 반대다

** state
- 대상 카드 ID
- 청구 월
- 결제 계좌 ID
- 결제 금액
- 결제 방식        전체 / 분할
- 할부 개월        (분할일 때)
- 처리안 / 승인 상태 / 요청 ID / 실패 사유

** 필요 함수
- 카드 해소 / 계좌 해소              (공통)
- 요금 조회(billing_query)
- 명세서 조회(billing_statement)
- 결제 검증(billing_validate)        -> 불가 분기
      결제 계좌 잔액 < 결제 금액
      이미 납부 완료된 청구
      분할 개월 수가 허용 범위 밖
      결제 금액이 0 이하이거나 청구 총액 초과
- 처리안 생성                        * 계산만. 저장 없음
- 승인                               (공통 노드. interrupt만)
- 실행 직전 재검증                   승인 후 잔액이 달라졌으면 다시 승인
- 결제 실행(billing_pay)
      결제 계좌 잔액 차감
      출금 내역 1건 기록
      청구 상태 변경 (전체결제 -> 완납 / 분할 -> 회차 진행)
      * 세 가지를 한 번에 저장한다. 하나만 반영되면 안 된다
- 저장 / requests 기록               (공통)

- 현재 상태        전이 가능 여부 판단용

      예: 분실 정지된 카드를 잠금 해제 -> "분실 정지는 해제할 수 없습니다"

      카드 종류 / 연결 계좌 존재 / 카드 이름
- 처리안 생성                        * 계산만. 저장 없음
- 승인                               (공통 노드)          <- 원본에 없던 것
- 카드 등록(card_setting_register)
- 카드 해지(card_setting_cancel)     status -> cancelled
- 비밀번호 변경(card_setting_change_password)
- 상태 변경(card_setting_change_status)   분실 / 신고 / 잠금 / 해제 공용
- 별칭 변경(card_setting_change_nickname)
- 저장 / requests 기록               (공통)

* 재발급 : CardReissueAgent  [수정]
  (원본에서 "분실/신고/재발급" 한 줄이던 것을 4개 업무로 펼침)

** 기능
- 재발급 신청
- 재발급 신청 조회
- 배송지 수정
- 신청 취소

** state
- 대상 카드 ID
- 신청 ID
- 배송지          집 / 회사
- 요청 유형        신청 / 조회 / 배송지수정 / 취소
- 처리안 / 승인 상태 / 요청 ID / 실패 사유

** 필요 함수
- 카드 해소                          (공통)
- 신청 자격 검증(reissue_validate_apply)
      대상 카드가 정지 상태여야 한다
      같은 카드에 취소되지 않은 신청이 이미 있으면
      새로 만들지 않고 기존 신청을 안내한다
- 배송지 확인(reissue_check_address)
      집 / 회사 중 선택. 미지정이면 물어본다
- 신청 조회(reissue_query)
      배송지와 처리 상태를 안내한다
      대상이 불명확하면 신청 목록을 주고 고르게 한다
      신청이 없으면 "기록이 없음"을 안내한다
- 수정·취소 가능 검증(reissue_validate_modify)      <- 핵심 분기 조건
      received            -> 수정·취소 가능
      making / shipping   -> 불가 안내 (제작이 시작됨)
      cancelled           -> 이미 취소된 신청
- 처리안 생성                        * 계산만. 저장 없음
- 승인                               (공통 노드)
- 신청 실행(reissue_apply)
      * 신청을 접수해도 기존 카드의 정지 상태는 그대로 유지한다
- 배송지 변경(reissue_change_address)
- 신청 취소(reissue_cancel)
- 저장 / requests 기록               (공통)

■ 오타 / 이름

■ 먼저 확인 : 계좌·카드 블록에서 "(공통)"으로 넘긴 것들

  계좌·카드 수정본에서 아래 항목들을 공통으로 올려놨다. 전부 여기 모여야 한다.

      계좌 해소 / 카드 해소            이체·조회·설정·결제·재발급 전부가 쓴다
      처리안 제시
      승인 (interrupt)
      실행 직전 재검증
      저장 (실패 시 이전 상태 유지)
      처리 기록
      결과 문장 정리
      도메인 반송 (Supervisor 재분류)
      후속 업무 이어가기 (정지 후 재발급)

  원본 공통 함수는 5개뿐이라 위의 절반도 담지 못한다.


■ 함수 5개와 기능 8개가 서로 대응되지 않는다

  기능              원본 함수                        상태
  ----------------  -------------------------------  ------------------------
  추가 질문         common_check_missing_information  있음
  대화 확인         common_check_context              있음
  승인/거절         common_response                   있음
  불가 안내         (없음)                            함수 없음
  사용자 확인       (없음)                            함수 없음. 아래 (1)로 추가
  결과 확인         common_result 와 겹침             저장과 섞여 있음
  내용 저장         common_result                     결과 확인과 한 함수
  오류 복구         common_error                      있음

  -> 둘의 차이  [결정됨]
        대화 확인   = 이전 대화의 맥락을 확인하는 것          common_check_context
                      "그 카드", "아까 그 계좌"가 무엇을 가리키는지 찾는다
        사용자 확인 = 확신할 수 없을 때 사용자에게 물어 확정하는 것
                      후보가 여러 개이면 목록을 주고 고르게 한다
     두 개는 합치지 않고 따로 둔다.
     맥락으로 찾는 것과, 못 찾았을 때 되묻는 것은 하는 일이 다르다.

  -> "불가 안내"는 기능에만 있고 함수가 없다. 추가한다.


■ common_result 가 두 가지를 섞고 있다

  "결과/변경 내용 저장" 한 함수에 서로 다른 두 일이 들어 있다.
      (가) 변경된 데이터를 파일에 저장한다      - 실패할 수 있다. 롤백이 필요하다
      (나) 사용자에게 결과를 안내한다            - 실패하지 않는다
  (가)가 실패했는데 (나)가 "완료됐습니다"를 출력하면 거짓말이 된다.
  -> 두 함수로 분리한다.  common_save  /  common_report


■ 추가해야 할 공통 함수

  (1) 대상 해소(common_resolve_target)
      별명·카드이름 -> ID
      소유자로 먼저 거른 뒤 이름을 맞춘다
          후보 0개     -> 불가 안내
          후보 1개     -> 확정
          후보 2개 이상 -> (1-b) 사용자 확인으로 넘긴다
      * 계좌·카드·청구서 에이전트가 전부 쓴다. 가장 많이 불리는 공통 함수다

  (1-a) 맥락 확인(common_check_context)              = 원본의 "대화 확인"
      "그 카드", "아까 그 계좌", "방금 그거" 가 무엇을 가리키는지
      이전 대화에서 찾는다
      찾았더라도 확신할 수 없으면 (1-b)로 넘긴다

  (1-b) 사용자 확인(common_confirm_target)           = 원본의 "사용자 확인"
      후보가 여러 개이거나 확신할 수 없을 때 사용자에게 물어 확정한다
      목록을 보여주고 고르게 한다
      * (1-a)가 "찾는 것", (1-b)가 "되묻는 것"이다. 하는 일이 다르므로 따로 둔다

  (1-c) 인증(common_authenticate)                    <- 결정 (다)
      민감한 업무(이체, 설정 변경, 결제) 전에 한 번 받는다
      수단 : 계좌 비밀번호 / PIN / 휴대전화번호 / 주민번호 뒷자리 중 택일
      처리안 제시 "전"에 둔다
      한 번 인증하면 얼마 동안 유효할지 정한다 (세션 단위 / 업무 단위)
      * 각 Agent에 두지 않는다. 업무마다 인증 규칙이 갈리면 관리가 안 된다

  (2) 승인 대기 판정(common_pending_check)          <- 흐름의 [분기 0]
      새 입력이 들어왔을 때, 승인 대기 중인 업무가 있는지 먼저 본다
      있으면 Supervisor 분류를 태우지 않고 그 업무로 보낸다
      * 이게 없으면 "응, 진행해"가 새 요청으로 잘못 분류된다

  (3) 응답 해석(common_interpret_response)
      자연어 응답을 승인 / 거절 / 취소 / 수정 중 하나로 매핑한다
          "응 진행해", "ㅇㅇ", "해줘"        -> 승인
          "아니", "취소할게", "하지마"        -> 거절
          "아니, 5만원만"                    -> 수정 (+ 바뀐 값)
      어느 쪽인지 확신할 수 없으면 되묻는다

  (4) 처리안 제시(common_propose)
      변경될 내용 전체를 보여준다. 계산만 하고 저장하지 않는다

  (5) 승인(common_approve)                          ** interrupt() 한 줄만 **
      다른 일을 절대 넣지 않는다. 재실행돼도 피해가 없어야 한다

  (6) 승인 전 수정(common_revise)
      처리안을 고치고 "전체 내용"을 다시 보여준 뒤 승인 단계로 되돌린다
      바뀐 부분만 보여주지 않는다. 사용자가 최종본을 보고 승인해야 한다

  (7) 실행 직전 재검증(common_revalidate)
      승인 시점과 지금의 전제(잔액, 카드 상태, 신청 상태)를 비교한다
      달라져서 처리 내용이 바뀌면 그대로 실행하지 않는다
          -> 다시 승인받거나 재요청 안내

  (8) 불가 안내(common_reject)                      <- 함수가 없던 것
      실행할 수 없는 이유를 말한다
      필요하면 어떤 정보를 넣어 다시 요청하면 되는지 알려준다

  (9) 저장(common_save)
      변경된 데이터를 파일에 쓴다
      실패하면 변경 전 상태를 유지한다 (부분 반영 금지)

 (10) 결과 안내(common_report)
      저장이 실제로 성공했을 때만 완료를 말한다
      성공 여부와 수치는 함수가 낸 값을 그대로 쓴다

 (11) 처리 기록(common_log_request)
      요청 식별자 / 업무 종류 / 대상 / 처리 내용 / 상태(성공·실패·취소) / 시각
      * "아까 이체 됐어?" 같은 후속 조회의 근거가 된다

 (12) 후속 결과 조회(common_query_history)          <- 원본에 없던 기능
      대화 맥락으로 사용자가 가리키는 이전 요청을 찾아
      성공·실패·취소 여부와 처리 내용을 안내한다
      가리키는 대상이 불분명하면 목록을 주고 고르게 한다

 (13) 도메인 반송(common_reroute)
      하위 Agent가 "내 도메인 아님"을 반환하면 Supervisor로 되돌린다
      반송 횟수를 세어 무한 왕복을 막는다 (1회까지)

 (14) 후속 업무 이어가기(common_next_task)
      "정지하고 재발급해줘" 처럼 두 업무가 이어질 때
      1번이 끝난 뒤 2번으로 넘긴다
      * 승인은 업무마다 따로 받는다. 몰아서 받지 않는다
      * 2번이 실패해도 이미 끝난 1번은 되돌리지 않는다


■ 패턴 정리

  CommonWorkflow
      위 공통 함수들을 각 업무 흐름이 공유한다.
      Supervisor의 라우팅 대상이 아니다. 흐름 중간에 끼어드는 단계다.

  HITL (interrupt / resume)
      승인 노드에는 interrupt() 외에 아무것도 두지 않는다.
      계산 / 승인 / 실행을 노드 3개로 쪼갠다. (기본 설계 원칙 참고)

  checkpoint
      ** 앞선 메모 정정 **
      "checkpoint를 각 노드에 두어야 한다"가 아니다.
      그래프를 compile할 때 checkpointer를 하나 붙이면
      모든 노드 경계에서 상태가 자동으로 저장된다.
          graph = builder.compile(checkpointer=...)
      노드마다 따로 설정하는 것이 아니다.
      실행할 때 thread_id를 함께 넘겨야 같은 대화로 이어진다.
      대화 세션 하나 = thread_id 하나. main.py에서 정한다.
      subgraph를 노드로 등록하면 부모의 checkpointer를 그대로 물려받는다.

  retry
      어디에 붙일지 정해야 한다.
      -> 저장 실패에만 붙인다. 승인·실행에는 붙이지 않는다.
         승인을 자동 재시도하면 사용자에게 같은 질문을 반복하게 된다.

  recovery (재시작 / 장애 복구)
      프로그램을 다시 켰을 때 진행 중이던 업무가 있으면 확인하고 이어서 처리한다.
      ** 이전에 받아둔 승인만으로 변경을 자동 실행하지 않는다. **
      복구 시점에 다시 확인을 받는다.
      -> 이유: 프로그램이 꺼져 있는 동안 잔액·카드 상태가 달라졌을 수 있다.
               (7) 실행 직전 재검증과 같은 이유다.


■ 공통 노드 최종 목록

      common_pending_check        승인 대기 판정 (분기 0)
      common_resolve_target       대상 해소 (계좌 / 카드 / 청구서 / 신청)
      common_check_context        맥락 확인 ("그 카드"가 무엇인지 찾기)
      common_confirm_target       사용자 확인 (후보가 여러 개일 때 고르게 하기)
      common_authenticate         인증
      common_ask_missing_info     부족 정보 질문
      common_propose              처리안 제시
      common_approve              승인 (interrupt 전용)
      common_interpret_response   승인 / 거절 / 취소 / 수정 해석
      common_revise               승인 전 수정
      common_revalidate           실행 직전 재검증
      common_reject               불가 안내
      common_save                 저장 (실패 시 이전 상태 유지)
      common_report               결과 안내
      common_log_request          처리 기록
      common_query_history        후속 결과 조회
      common_error                오류 / 복구 / 재시도
      common_reroute              도메인 반송
      common_next_task            후속 업무 이어가기


■ 어느 업무가 어떤 공통 노드를 쓰는가

  모든 업무        pending_check -> (분류) -> check_context -> resolve_target
                       -> confirm_target(필요시) -> ask_missing_info
  조회만           ... -> 실행 -> report
  변경 업무        ... -> authenticate -> propose -> approve -> revalidate
                       -> 실행 -> save -> log_request -> report
  실패 시          reject (실행 전)  또는  error (실행·저장 중)
  연속 업무        위 흐름이 끝난 뒤 next_task

4. 청구서 · 납부      [검토 후 제외]

  한때 별도 카테고리로 넣으려 했으나 제외했다. 기록만 남긴다.

  제외 이유
      카드 요금 결제와 흐름이 사실상 같다.
          낼 것 목록 조회 -> 상세 확인 -> 금액 확인 -> 승인
          -> 계좌 차감 + 거래 기록 + 상태 변경 -> 결과 안내
      다른 것은 "돈을 낼 대상이 카드사냐 공과금 기관이냐" 뿐이고,
      데이터 이름만 다를 뿐 처리 로직이 갈리지 않는다.
      에이전트 3개(BillAgent / BillQueryAgent / BillPaymentAgent)와
      1단 분류 항목 하나가 늘어나는 것에 비해 얻는 것이 없다.

  대신 카드로 옮긴 것
      부분 결제   "카드값 5만원만 낼게"   -> CardBillingAgent
                  (청구서의 "부분 납부"에 해당)
      일괄 결제   카드 여러 장 한 번에     -> CardBillingAgent
                  (청구서의 "일괄 납부"에 해당)
      * 일괄 결제를 반드시 남긴 이유 :
        "건별로 저장하고, 하나 실패해도 앞의 것은 유지"라는 규칙을
        보여줄 수 있는 유일한 자리다.
        나눠 이체의 "전부 아니면 전무"와 정확히 반대되는 사례라
        둘을 같이 두면 저장 규칙 설계가 드러난다.

  결과
      에이전트 9개 -> 7개
      1단 분류 : 계좌 / 카드
      기능 손실 없음

- Supervisor 라우터 껍데기 (계좌만 연결)
- AccountQueryAgent - 계좌 목록/잔액 조회
- 최종 출력 문장 정리
* 목적: 승인이 없는 가장 단순한 업무로 전체 경로를 먼저 완성한다.
        라우팅이 되는지를 맨 마지막이 아니라 여기서 확인한다.

2. 즉시이체 1개로 변경 흐름 완성  (쓰기 + 승인)
- 공통 노드 먼저 구현
  : 부족 정보 질문 / 처리안 제시 / interrupt-resume 승인·거절 / 오류·복구 / 저장
- TransferAgent - 계좌 확인, 잔액 확인, 처리안 생성, 실행, 거래내역 기록
* 목적: 조회 / 변경 / 승인 / 거절 / 실패 다섯 분기를 여기서 전부 완성한다.
        (제출물이 요구하는 분기 조건이 정확히 이 다섯 가지)
* 공통 노드(HITL)를 1단계 뒤가 아니라 여기 앞에 두는 이유:
  승인은 나중에 붙이는 기능이 아니라 checkpointer, interrupt 지점,
  state 구조를 결정하는 뼈대다. 기능을 다 만든 뒤 붙이면 전부 뜯어고치게 된다.

3. 계좌 나머지 기능 추가
- 조건부 이체 / 나눠 이체 / 계좌 등록 / 이름·용도 변경 / 예약 이체
- 2단계에서 만든 틀에 붙이는 작업이 된다.
- 인증(common_authenticate)을 여기서 붙인다.

4. 카드 기능 추가
- 조회 -> 설정(정지/잠금/해제/별칭) -> 재발급 -> 결제 순서.
- 재발급은 신청 상태(접수/제작중/배송중)에 따라 갈리므로 뒤에 붙인다.
- 결제는 청구 데이터가 필요하므로 마지막에 한다.
- 일괄 결제에서 건별 저장 규칙을 확인한다. 나눠 이체와 정확히 반대다.

5. 전체 통합 점검
- Supervisor 1단 분류에 계좌 / 카드가 모두 연결됐는지
- 반송 경로가 동작하는지
- 재시작 후 복구가 동작하는지
