virtual-bank-agent 설계 기획서 (정리본)

기본 설계 원칙
- supervisor 패턴으로 각 Agent로 나누어서 노드 및 그래프를 구현한다.
- 각 Agent는 compile한 subgraph를 supervisor 그래프의 노드로 등록한다.
 * tool로 감싸지 않는다. interrupt 재개 시 노드를 처음부터 다시 실행하므로
   tool로 감싸면 재실행 범위가 커져 부작용이 두 번 일어난다.
- 데이터에 쓰기가 일어나는 모든 업무는 HITL로 승인을 받고 실행한다.
 * 읽기만 하는 조회는 승인 없이 출력한다.
- interrupt가 있는 노드에는 부작용을 두지 않는다.
 * 처리안 생성 / 승인 / 실행을 노드 3개로 쪼갠다.
- 공통 부분은 agent를 적용하지 않고 공통 노드로 만든다.
 * 공통은 supervisor의 라우팅 대상이 아니다. 흐름 중간에 끼어드는 단계다.
- 성공 여부와 금액 등 수치는 함수가 낸 값을 그대로 쓴다.
 * llm은 문장만 다듬는다. 성공 여부를 판단하거나 수치를 만들지 않는다.


흐름
입력(자연어)
-> 승인 대기 중인 업무가 있는가
 -> 있음 : 승인/거절/수정으로 해석 -> 해당 업무 재개
 -> 없음 : Virtual_Bank_Supervisor_Agent (1단 분류 : 계좌/카드)
-> 도메인 Agent (2단 분류)
 * 내 도메인이 아니면 supervisor로 반송 후 재분류 (1회까지)
-> 기능 Agent (3단 분류)
-> 필요 정보 확인 -> 부족하면 질문 후 복귀
-> 실행 가능한가 -> 불가하면 사유 안내 후 종료
-> 데이터를 변경하는가
 -> 아니오 : 실행 -> 결과 반환
 -> 예 : 인증 -> 처리안 제시 -> 승인 요청(interrupt)
        -> 승인 : 실행 직전 재검증 -> 실행 -> 저장 -> 처리 기록
        -> 거절 : 변경 없이 종료
        -> 수정 : 처리안 갱신 후 전체 내용 다시 제시
        -> 실행/저장 실패 : 변경 전 상태 유지 후 사유 안내
-> Virtual_Bank_Supervisor_Agent에서 최종 문장 정리 후 출력
* 각 기능별 공통 노드를 두어 승인, 맥락확인, 사용자 확인, 오류, 복구 등을 담당한다.


1. 계좌
* 계좌 : AccountAgent
- 요청을 받아 분류하고 기능에 맞는 agent에 전달한다.
** 필요 함수
- 요청 분류(account_router) -> 이체, 조회, 설정
- 도메인 반송(공통)
- 정보 전달(엣지/Command -> 각 에이전트)
* 필요 정보 확인과 부족 정보 질문은 3단으로 내린다.
  종류가 정해지기 전에는 무엇이 부족한지 알 수 없다.


* 이체 : TransferAgent
** state
- 보내는 계좌
- 받는 계좌 목록 [{계좌, 금액}]
- 이체 유형 (즉시/조건부/나눔)
- 남길 금액 (조건부)
- 총 이체액
- 대상 구분 (본인/타인)
- 은행 구분 (자행/타행)
- 받는 은행명
- 예금주 이름
- 비밀번호 (검증 후 즉시 폐기)
- 예약 시간 (선택)
- 계좌 잔고 스냅샷
- 처리안
- 승인 상태
- 요청 ID
- 실패 사유

** 필요 함수
- 이체 유형 분기/요청 분류(transfer_router) -> 즉시, 조건부, 나눔
- 계좌 확인(transfer_account_verification)
- 비밀번호 확인(transfer_check_password)
- 잔액 확인(transfer_check_balance)
- 이체액 계산(transfer_calculate_amount)
- 예약 여부 확인(transfer_check_reservation)
- 검증(transfer_validate)
- 처리안 생성(transfer_build_proposal)
- 승인 요청(공통)
- 실행 직전 재검증(transfer_revalidate)
- 이체 실행(transfer_execution)
- 결과 반환(공통)

** 기능
- 즉시 이체
- 조건부 이체 (남길 금액 기준)
- 여러 계좌로 나눠 이체
- 본인 이체
- 타인 이체
- 같은/다른 금융 이체
- 이체 예약 설정
- 예약 조회/취소

** 분기 조건
- 이체액 0 이하 -> 불가
- 원 단위 정수 아님 -> 불가
- 출금 계좌 잔액 < 총액 -> 불가
- 출금 계좌 == 입금 계좌 -> 불가
- 타행인데 은행 미지정 -> 질문
- 예약 일시가 과거 -> 불가
- 승인 후 잔액이 달라져 이체액이 바뀜 -> 재승인 또는 재요청 안내

** 처리 규칙
- 이체 실행 시 거래 내역에 출금 1건, 입금 1건을 기록한다.
- 나눠 이체는 전체를 한 번에 반영한다. 일부만 반영하지 않는다.
- 예약은 시각이 되면 처리한다.
 * 프로그램이 켜져 있으면 입력을 받을 때마다 지난 예약을 확인한다.
 * 꺼져 있었으면 다음 시작 시 지난 예약을 확인한다.
 * 실행 시점에 잔액이 부족하면 실행하지 않고 실패로 남긴다.


* 조회 : AccountQueryAgent
** state
- 조회 종류 (계좌목록/총액/거래내역)
- 조회할 계좌
- 기간 (시작일, 종료일)
- 금액 조건
- 거래 유형 (입금/출금/결제)
- 검색어

** 필요 함수
- 요청 분류(account_query_router) 분기
- 기준일 정의(get_today)
- 계좌 목록 조회(account_query_accounts)
- 잔액 확인(account_query_check_balance)
- 잔액 합산(account_query_total_balance)
- 거래 내역 조회(account_query_transactions)
- 결과 반환(공통)

** 기능
- 계좌 목록 및 잔액 조회
- 잔액 합산
- 거래 내역 조회 (기간/금액/유형/검색어)

** 규칙
- 기준일은 프로그램에서 상수로 정한다.
- 이번 달 = 기준일이 속한 달, 이번 주 = 월요일~일요일
- 기간은 시작일과 종료일을 포함한다.
- 최근순으로 정렬한다.
- 카드 결제 건은 사용한 카드도 함께 표시한다.
- 필터는 함수를 쪼개지 않고 조건 조합으로 받는다.


* 설정 : AccountSettingAgent
** state
- 설정할 계좌
- 요청 유형 (이름/용도/등록/등록조회/삭제)
- 이름
- 용도
- 등록 정보 (은행명/계좌번호/예금주/별명)
- 처리안
- 승인 상태
- 요청 ID
- 실패 사유

** 필요 함수
- 요청 분류(setting_router)
- 이름 검증(setting_validate_name)
- 용도 검증(setting_validate_purpose)
- 등록 정보 검증(setting_validate_register)
- 처리안 생성
- 승인 요청(공통)
- 이름 변경(setting_change_name)
- 용도 변경(setting_change_use)
- 계좌 등록(setting_register_account)
- 등록 계좌 조회/삭제(setting_query_account, setting_delete_account)
- 결과 반환(공통)

** 기능
- 이름/용도 변경
- 계좌 등록 (자행/타행 동일 방식, 은행명 입력)
- 등록 계좌 조회/삭제

** 분기 조건
- 이름 공백 제거 후 길이 초과/미달 -> 불가
- 같은 소유자의 다른 계좌와 이름 중복 -> 불가
- 용도 길이 초과 -> 불가
- 은행명 + 계좌번호가 이미 등록됨 -> 기존 등록 안내

** 규칙
- 용도는 자유 입력으로 받는다. 정해진 목록에서 고르게 하지 않는다.
 * 검증은 길이 제한만 한다. 중복은 허용한다.

** 기능
- 은행별 카드 조회

- 멤버십 조회
- 이용내역 조회

** 규칙
- 카드 조회 결과에 반드시 상태를 포함한다.

- 실 카드 번호는 마스킹하지 않고 전체를 보여준다.
 * 본인 인증을 거친 세션이므로 가린 번호를 다시 보여줄 이유가 없다.
 * 단, 인증이 안 된 상태이면 인증을 먼저 받는다.


* 결제 : CardBillingAgent
** state
- 대상 카드 목록 (일괄 결제 시 여러 장)
- 청구 월
- 결제 계좌
- 결제 금액 (부분 결제 시 사용자가 지정한 금액)
- 총 결제액
- 결제 방식 (전체/부분/분할/일괄)
- 할부 개월 (분할일 때)
- 계좌 잔고 스냅샷
- 처리안
- 승인 상태
- 요청 ID
- 건별 결과 (일괄일 때 완료/실패/미처리)
- 실패 사유

** 필요 함수
- 요청 분류(cardbilling_router)
- 요금 조회(cardbilling_charge_search)
- 명세서 조회(cardbilling_statement)
- 결제 검증(cardbilling_validate)
- 처리안 생성
- 승인 요청(공통)
- 실행 직전 재검증
- 전체 결제(cardbilling_payment_full)
- 부분 결제(cardbilling_payment_partial)
- 분할 결제(cardbilling_payment_installment)
- 일괄 결제(cardbilling_payment_batch)
- 결과 반환(공통)

** 기능
- 요금 조회
- 명세서 조회
- 요금 결제 (전체)
- 부분 결제 (금액 지정, "카드값 5만원만 낼게")
- 분할 결제 (할부)
- 일괄 결제 (카드 여러 장 한 번에)

** 청구 상태
- unpaid   미납
- partial  일부 납부
- paid     납부 완료
* 남은 금액 = 청구 총액 - 납부한 금액

** 분기 조건
- 결제 계좌 잔액 < 결제 금액 -> 불가
- 이미 납부 완료(paid)된 청구 -> 다시 처리하지 않고 안내
- 결제 금액이 0 이하 -> 불가
- 결제 금액 > 남은 금액 -> 불가 (남은 금액을 안내하고 다시 요청받는다)
- 할부 개월 수가 범위 밖 -> 불가
- 청구 내역이 없음 -> 불가

** 처리 규칙
- 전체 결제 : 계좌 잔액 차감 + 출금 내역 기록 + 청구 상태(paid)를 한 번에 저장한다.
              하나라도 실패하면 전부 되돌린다.
- 부분 결제 : 계좌 잔액 차감 + 출금 내역 기록 + 남은 금액 갱신을 한 번에 저장한다.
              남은 금액 > 0 이면 partial, 0 이 되면 paid 로 바꾼다.
              부분 결제도 승인을 받는다. 결제액과 남은 금액을 처리안에 보여준다.
- 분할 결제 : 개월 수만큼 회차를 만든다. 회차별 금액과 남은 회차를 관리한다.
- 일괄 결제 : 결제일이 빠른 청구부터 건별로 처리하고 건별로 저장한다.
              부분 납부된 건은 남은 금액만 낸다.
              잔액 부족인 건은 그대로 두고 다음 건을 확인한다.
              저장 실패 시 그 건을 미반영으로 두고 남은 처리를 중단한다.
              이미 저장된 결제는 유지한다.
              결과를 완료/실패/미처리로 나누어 안내한다.
* 일괄 결제의 승인은 전체에 대해 한 번만 받는다.
* 나눠 이체는 전부 아니면 전무, 일괄 결제는 건별 확정이다. 규칙이 반대다.


* 설정 : CardSettingAgent
** state
- 설정할 카드
- 요청 유형 (등록/해지/비밀번호/분실신고/잠금/해제/별칭)
- 현재 상태
- 변경 내용
- 처리안
- 승인 상태
- 요청 ID
- 실패 사유

** 필요 함수
- 요청 분류(card_setting_router)
- 상태 전이 검증(card_validate_transition)
- 비밀번호 검증(card_validate_password)
- 별칭 검증(card_validate_nickname)
- 등록 정보 검증(card_validate_register)
- 처리안 생성
- 승인 요청(공통)
- 카드 등록/해지(card_setting_register, card_setting_cancel)
- 비밀번호 변경(card_setting_change_password)
- 상태 변경(card_setting_change_status)
- 별칭 변경(card_setting_change_nickname)
- 결과 반환(공통)

** 기능
- 카드 등록/해지
- 비밀번호 변경
- 분실 신고 (분실 및 정지)
- 일시 잠금 / 잠금 해제
- 별칭 변경

** 카드 상태
- active     사용 가능
- locked     일시 잠금
- lost       분실 및 정지
- cancelled  해지됨
* 분실/도난/부정사용은 모두 lost로 처리하고 사유(report_reason)만 기록한다.

** 상태 전이
- active -> locked   일시 잠금
- active -> lost     분실 신고
- active -> cancelled 해지
- locked -> active   잠금 해제
- locked -> lost     분실 신고
- locked -> cancelled 해지
- lost -> active     불가 (분실 정지는 해제할 수 없다)
- lost -> locked     불가
- cancelled -> 무엇이든 불가
- 이미 같은 상태 -> 불가 안내

** 규칙
- 해지는 목록에서 지우지 않고 cancelled로 둔다. 지우면 이용 내역이 참조를 잃는다.
- 일시 잠금은 계좌 잔액과 기존 거래를 건드리지 않는다.

- 처리안
- 승인 상태
- 요청 ID
- 실패 사유

** 필요 함수
- 요청 분류(reissue_router)
- 신청 자격 검증(reissue_validate_apply)
- 배송지 확인(reissue_check_address)
- 신청 조회(reissue_query)
- 수정/취소 가능 검증(reissue_validate_modify)
- 처리안 생성
- 승인 요청(공통)
- 신청 실행(reissue_apply)
- 배송지 변경(reissue_change_address)
- 신청 취소(reissue_cancel)
- 결과 반환(공통)

** 기능
- 재발급 신청
- 재발급 신청 조회
- 배송지 수정
- 신청 취소

** 신청 상태
- received   접수     수정/취소 가능
- making     제작중   수정/취소 불가
- shipping   배송중   수정/취소 불가
- cancelled  취소됨

** 분기 조건
- 대상 카드가 lost가 아님 -> 불가
- 취소되지 않은 기존 신청이 있음 -> 기존 신청 안내
- 배송지 미지정 -> 질문
- 신청 상태가 making/shipping -> 수정/취소 불가 안내
- 신청 기록 없음 -> 기록 없음 안내

** 규칙
- 신청을 접수해도 기존 카드의 분실 정지는 유지한다.
- 제작/배송 상태는 테스트 데이터로 준비해 제한 동작을 확인한다.
- 실제 제작/배송 진행은 구현하지 않는다.


* 정지 후 재발급 연속 처리
- CardSettingAgent(분실 정지) -> 승인 1 -> 실행 -> 저장
- CardReissueAgent(재발급 신청) -> 승인 2 -> 실행 -> 저장
* 승인은 업무마다 따로 받는다. 몰아서 받지 않는다.
* 재발급이 실패하거나 거절되어도 이미 완료된 정지는 되돌리지 않는다.
* 이어서 처리할 후속 업무를 state에 남긴다.


3. 공통
* 적용할 패턴
- CommonWorkflow
- HITL
 * interrupt/resume
- checkpoint/recovery/retry

** 필요 함수
- 승인 대기 판정(common_pending_check)
- 맥락 확인(common_check_context)
- 사용자 확인(common_confirm_target)
- 대상 해소(common_resolve_target)

- 처리안 제시(common_propose)
- 승인(common_approve)
- 응답 해석(common_interpret_response)
- 승인 전 수정(common_revise)
- 실행 직전 재검증(common_revalidate)
- 불가 안내(common_reject)
- 저장(common_save)
- 결과 안내(common_report)
- 처리 기록(common_log_request)

- 오류/복구(common_error)
- 도메인 반송(common_reroute)
- 후속 업무 이어가기(common_next_task)

** 기능
- 추가 질문
- 대화(맥락) 확인
- 사용자 확인
- 본인 인증
- 승인/거절/취소
- 승인 전 수정
- 불가 안내
- 결과 확인
- 내용 저장
- 처리 기록
- 후속 결과 조회
- 오류 복구
- 도메인 반송
- 후속 업무 이어가기

** 역할 구분
- 맥락 확인 : "그 카드", "아까 그 계좌"가 무엇인지 이전 대화에서 찾는다.
- 사용자 확인 : 확신할 수 없거나 후보가 여러 개일 때 목록을 주고 고르게 한다.
- 대상 해소 : 소유자로 거른 뒤 이름을 맞춰 ID로 바꾼다.
 * 후보 0개 -> 불가 안내 / 1개 -> 확정 / 2개 이상 -> 사용자 확인
- 저장 : 파일에 쓴다. 실패할 수 있다.
- 결과 안내 : 저장이 성공했을 때만 완료를 말한다.
 * 두 개를 한 함수에 두면 저장 실패인데 완료를 출력하게 된다.

** 인증
- 한 번 인증하면 그 세션 동안 유효하다. 업무마다 다시 받지 않는다.
 * 세션 = thread_id 하나 = 프로그램을 켜고 끌 때까지
- 인증은 처리안 제시 전에 받는다.
 * 승인 직후에 두면 인증이 틀렸을 때 처리안을 다시 만들어야 한다.
- 수단 : 계좌 비밀번호 / PIN / 휴대전화번호 / 주민번호 뒷자리 중 택일
- 재시작하면 인증은 풀린다. 복구 시점에 다시 받는다.

** 승인 규칙
- 승인 노드에는 interrupt만 둔다. 다른 일을 넣지 않는다.
- 자연어 응답을 승인/거절/취소/수정으로 매핑한다.
 * 확신할 수 없으면 되묻는다.
- 수정 시 바뀐 부분만 보여주지 않고 전체 내용을 다시 보여준다.

** checkpoint
- 그래프를 compile할 때 checkpointer를 하나 붙인다.
 * 노드마다 따로 두는 것이 아니다. 모든 노드 경계에서 자동 저장된다.
- 실행 시 thread_id를 넘긴다. 대화 세션 하나 = thread_id 하나.
- subgraph를 노드로 등록하면 부모의 checkpointer를 물려받는다.

** retry
- 저장 실패에만 붙인다.
- 승인과 실행에는 붙이지 않는다. 승인을 자동 재시도하면 같은 질문을 반복한다.

** recovery
- 재시작 시 진행 중이던 업무를 확인하고 이어서 처리한다.
- 이전 승인만으로 변경을 자동 실행하지 않는다. 복구 시점에 다시 확인받는다.
 * 꺼져 있는 동안 잔액과 카드 상태가 달라졌을 수 있다.


## 설계 순서
0-1.
- 초기 데이터 확장 (initial_data.json, data.json)
* 은행명 / 계좌번호 / 계좌 비밀번호 / 계좌 용도 / 등록 계좌
* 카드 비밀번호 / 멤버십 / 신용카드 청구·명세서 / 할부
* 예약 이체 목록 / 재발급 신청 목록 / 처리 기록
* 신용카드 최소 1장, 제작중·배송중 재발급 신청은 테스트 데이터로 미리 넣는다
* 데이터를 먼저 확정한다. 지금 데이터로는 계획한 기능 대부분이 성립하지 않는다.

0-2.
- 로그 구현
* 남기는 것 : 턴 / 라우팅 결과 / 노드 진입·이탈 / state 변경 / 이름-ID 해소
              파일 읽기·쓰기 / interrupt 멈춤·재개 / 예외
* interrupt 재개로 다시 도는 노드에는 (재실행) 표시를 붙인다
  재실행은 정상이다. 다만 재실행된 노드에서 저장이나 기록이 일어나면 버그다
* 비밀번호 / PIN / 주민번호 뒷자리는 마스킹한다. 카드번호와 계좌번호는 남긴다
* logs/ 날짜별 파일에 이어 쓴다. 재시작 전후를 한 파일에서 본다
* 콘솔 출력은 기본으로 끈다. --debug 를 주면 켠다
* LangSmith 는 LLM 호출을 보고, 파일 로그는 노드 흐름과 예외를 본다

0-3.
- data_store 구현
* ensure 작업본 없으면 원본에서 복사
* load  작업본 읽기
* save  작업본 쓰기
* reset 원본을 다시 복사해 초기 상태로
* 원본(initial_data.json)은 읽기만 한다. 조회·변경은 작업본(data.json)에만 일어난다.
* 복사 / 저장 / 실패를 전부 로그로 남긴다. 그래서 로그를 먼저 만든다.

## 결정된 것

- retry               저장 실패에만 붙인다

## 초안에서 바뀐 것
직접 작성한 초안을 AI 에이전트와 검토하면서 바꾼 내용이다.
초안 원문은 설계 초안/기획서_수기(초안).txt 에, 원본과 수정본 대조는
설계 중/기획서_수기(진행).txt 에 남겨 두었다.


1. 분기 조건 / 처리 규칙 섹션을 새로 넣었다
- 원래 : state, 필요 함수, 기능 세 가지만 적었다.
- 바꾼 것 : 각 업무에 ** 분기 조건, ** 처리 규칙, ** 상태 전이 섹션을 추가했다.
- 이유 : 기능 목록만 있으면 "언제 실패하고 언제 되돌아가는지"가 없다.
         과제가 요구하는 조회/변경/승인/거절/실패 분기를 적을 자리가 없었다.
         상의하면서 이 부분이 설계의 핵심이라는 걸 알게 되어 넣었다.

2. 공통 노드를 각 기능 흐름에 배치했다
- 원래 : 3. 공통 에 함수 이름만 모아 두었다.
- 바꾼 것 : 각 에이전트의 필요 함수 목록에 (공통) 표시로 끼워 넣었다.
- 이유 : 모아만 두면 어느 업무가 언제 그걸 부르는지 알 수 없다.
         승인/저장/해소가 실제로 어디에 끼어드는지 보이게 했다.

3. state에 승인 관련 항목을 넣었다
- 원래 : 업무에 필요한 값만 적었다. 승인 관련 필드가 하나도 없었다.
- 바꾼 것 : 처리안 / 승인 상태 / 요청 ID / 실패 사유를 모든 변경 업무에 추가했다.
- 이유 : HITL이 이 프로젝트의 핵심인데 그 상태를 담을 자리가 없었다.
         승인 대기 중에 무엇을 들고 있어야 하는지 생각하지 못했다.

4. 흐름에 되돌아오는 경로를 넣었다
- 원래 : 입력 -> 분류 -> 실행 -> 반환 한 방향이었다.
- 바꾼 것 : 정보 부족 / 승인 대기 / 거절 / 승인 전 수정 네 개의 복귀 경로를 넣었다.
- 이유 : 실제로는 되돌아가는 경우가 더 많은데 성공하는 경우만 그려 두었다.

5. 승인 대기 판정을 맨 앞에 넣었다
- 원래 : 들어오는 입력을 항상 새 요청으로 보고 분류했다.
- 바꾼 것 : 입력을 받으면 먼저 "승인 대기 중인 업무가 있는가"를 확인한다.
- 이유 : 승인 대기 중에 "응, 진행해"를 치면 그게 새 요청으로 분류된다.
         이 분기가 없으면 자연어 승인이 아예 동작하지 않는다.

6. 필요 정보 확인을 3단으로 내렸다
- 원래 : AccountAgent(2단)에 필요 정보 확인 / 부족한 정보 질문을 두었다.
- 바꾼 것 : 각 기능 에이전트(3단)로 내렸다.
- 이유 : 2단 시점에는 "이체"까지만 정해지고 유형을 모른다.
         즉시/조건부/나눔마다 필요한 정보가 달라서 무엇이 부족한지 판단할 수 없다.

7. 도메인 반송 경로를 넣었다
- 원래 : 없었다.
- 바꾼 것 : 하위 에이전트가 "내 도메인 아님"을 반환하면 supervisor로 되돌린다.
            반송 횟수를 세어 1회까지만 재분류한다.
- 이유 : 3단 계층 분류를 쓰기로 했으면 1단이 잘못 보냈을 때 복구할 길이 있어야 한다.
         계좌로 잘못 보내면 카드 기능에 영영 도달하지 못한다.

8. 승인을 부작용 없는 단독 노드로 분리했다
- 원래 : TransferAgent 안에 승인 요청 함수를 두었다.
- 바꾼 것 : 처리안 생성 / 승인 / 실행을 노드 3개로 쪼개고 승인은 공통으로 올렸다.
            승인 노드에는 interrupt만 두고 저장이나 기록을 넣지 않는다.
- 이유 : interrupt로 멈췄다가 재개하면 멈춘 줄부터 이어지는 것이 아니라
         그 노드를 처음부터 다시 실행한다.
         승인 노드에 저장이 있으면 두 번 저장된다.
         checkpoint를 노드마다 두는 것으로 잘못 알고 있었는데,
         compile할 때 하나 붙이면 모든 노드 경계에서 저장된다는 것도 이때 알았다.

9. 카드 상태와 재발급 신청 상태를 정의했다
- 원래 : 상태 개념이 없었다. 분실 / 신고 / 재발급 세 갈래로만 나눴다.
- 바꾼 것 : 카드 상태(active/locked/lost/cancelled)와 전이표,
            재발급 신청 상태(received/making/shipping/cancelled)를 정의했다.
- 이유 : "분실 정지된 카드는 잠금 해제로 되돌릴 수 없다",
         "제작이 시작되면 신청을 수정할 수 없다" 같은 것이 전부 분기 조건인데
         상태를 정의하지 않으면 적을 수가 없다.
         분실과 신고는 결과가 같아서 하나로 합치고 사유만 기록하기로 했다.

10. 카드 에이전트를 2개에서 4개로 나눴다
- 원래 : CardCheckAgent(조회/결제), CardSettingAgent(설정) 2개였다.
- 바꾼 것 : CardQueryAgent / CardBillingAgent / CardSettingAgent / CardReissueAgent
- 이유 : 층을 나눈 목적이 각 층의 선택지를 3~4개로 줄이는 것인데,
         2개로 두면 3단 선택지가 9개, 7개가 되어 목적과 반대가 된다.
         조회와 결제는 필요한 정보가 완전히 달라서 한 에이전트에 두면
         필요 정보 확인 단계에서 또 갈라야 한다.

11. 청구서 카테고리를 넣었다가 뺐다
- 원래 : 없었다.
- 바꾼 것 : 별도 카테고리로 설계했다가 제외하고, 부분 결제와 일괄 결제만
            카드 결제로 옮겼다.
- 이유 : 카드 요금 결제와 흐름이 사실상 같아 에이전트만 3개 늘어난다.
         다만 일괄 처리는 "건별로 저장하고 하나 실패해도 앞의 것은 유지"라는
         규칙을 보여주는 유일한 자리라서 카드로 옮겨 살렸다.
         나눠 이체의 "전부 아니면 전무"와 정확히 반대되는 사례다.

12. 설계 순서를 가로에서 세로로 바꿨다
- 원래 : 계좌 전부 -> 카드 전부 -> 통합 순서였다.
- 바꾼 것 : data_store -> 계좌 조회 1개로 관통 -> 즉시이체 1개로 5분기 완성
            -> 확장 순서로 바꿨다.
- 이유 : 원래 순서는 마지막 통합 전까지 입력부터 출력까지 도는 업무가 하나도 없다.
         공통 노드(승인)를 1단계 맨 뒤에 두었는데, 승인은 나중에 붙이는 기능이 아니라
         그래프 구조를 정하는 뼈대라 앞으로 당겼다.
         data_store가 순서에 아예 빠져 있던 것도 이때 발견했다.

13. 데이터 구조를 기능에 맞게 늘렸다
- 원래 : 기획 단계라 필드를 정하지 않았다.
- 바꾼 것 : 은행명 / 계좌번호 / 계좌 용도 / 카드 비밀번호 / 멤버십 /
            신용카드 청구와 명세서 / 할부 / 예약 이체 목록 /
            재발급 신청 목록 / 처리 기록을 두기로 했다.
- 이유 : 기능을 정하고 나니 그 기능이 쓸 필드가 필요했다.
         기능에 맞춰 데이터를 정하는 순서로 진행했다.
