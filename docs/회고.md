# 회고

> 개발 기록(기획서 12장, 커밋, 정리 과정)에서 사실을 모아 쓴 초안입니다. 느낀 점은 직접 다듬어 주세요.

## 1. 배운 점

**interrupt 는 "멈춘 줄부터" 가 아니라 "그 노드를 처음부터" 다시 실행한다.**
처음에는 승인 노드 안에서 저장까지 하려 했는데, 재개하면 노드 전체가 다시 돌아 저장이 두 번 일어날 수 있다는 걸 알고
처리안(계산만) / 승인(interrupt 한 줄) / 실행(승인 뒤에만) 세 노드로 나눴다. 같은 이유로 서브그래프를 tool 로 감싸지 않고 노드로 넣었다.
로그에 `(재실행)` 표시를 붙여, 재개할 때 다시 도는 게 정상인지 버그인지 눈으로 구분할 수 있게 했다.

**LLM 에게 맡길 일과 Python 에게 맡길 일을 나누는 것이 가장 중요했다.**
LLM 은 사용자 말에서 값을 뽑고(출금 계좌, 금액, 기간 …) 분류만 한다. 이름을 ID 로 바꾸기, 잔액 검사, 금액 계산, 성공 여부는 전부 `functions/` 가 한다.
초안에는 "마지막에 LLM 이 보기 좋은 말로 정리" 단계가 있었는데, 금액을 LLM 이 다시 쓰면 틀릴 수 있어서 뺐다.
pydantic 타입(`date`, `datetime`, `Literal`)으로 LLM 출력 형식을 고정하면 틀린 값이 코드 안으로 들어오지 못한다.

**HITL 은 "승인 노드 하나" 가 아니라 흐름 전체의 뼈대다.**
승인 대기 중에 친 "응, 진행해" 가 새 요청으로 분류되지 않으려면 입력마다 "멈춘 업무가 있는가"(분기 0)를 먼저 봐야 했고,
승인·거절·수정·다른 요청·모름을 가르는 해석 노드, 거절도 처리 기록에 남기는 마무리 노드가 같이 필요했다.
그래서 2단계에서 공통(승인·저장·기록)을 먼저 완성하고 기능을 붙였는데, 이후 기능은 같은 틀에 끼우는 일이 되어 훨씬 빨랐다.

**설계는 구현하면서 계속 바뀐다. 바뀐 이유를 적어 두는 게 중요하다.**
공통 노드를 17개 계획했지만 실제로는 8개가 되었다. 무엇이 부족한지, 무엇을 물을지가 업무마다 달라 공통으로 두면 안에서 또 갈라야 했기 때문이다.
이체 유형을 분류하는 노드도 계획했지만, 한 요청이 조건부 + 예약처럼 여러 축을 같이 가져서 분류 대신 "뽑은 값이 있는가" 로 정하게 바꿨다.
바꿀 때마다 기획서에 이유를 남겨 두어서, 최종 설계를 정리할 때 그대로 쓸 수 있었다.

**한 단계씩 만들고 확인하고 커밋하는 방식이 결국 빨랐다.**
단계마다 확인 스크립트를 만들어 두어, 뒤에서 코드를 정리(중복 합치기, 파일 나누기)할 때 같은 스크립트로 바로 확인할 수 있었다.

## 2. 어려웠던 점과 해결 과정

| 어려웠던 점 | 원인 | 해결 |
|---|---|---|
| 지난 요청의 값이 새 요청에 섞임 | 체크포인터가 thread 별로 State 를 계속 들고 있음 | `new_request()` 가 새 요청마다 이번 업무 칸을 모두 비우고, 세션 인증·직전 이체만 남김 |
| 노드에서 예외가 난 뒤 다음 입력이 이전 요청을 다시 실행 | 예외가 나도 그래프가 그 노드 앞에 멈춘 채(`next`)로 남아, 대기로 판정됨 | 사용자에게 물어본(interrupt) 경우만 대기로 보도록 분기 0 을 고침 (`snapshot.interrupts`) |
| 예약 시각이 9시간 밀림 | LLM 이 시각 끝에 `Z`(UTC)를 붙여 줌 | 사용자가 말한 시각은 항상 이 컴퓨터 기준이므로 시간대를 떼고 씀 |
| "생활비 카드" 에 "생활비 신용카드" 까지 걸려 엉뚱한 카드를 바꿀 뻔함 | 이름에 글자가 들어 있으면 모두 후보 | 정확히 같은 이름을 먼저 보고, 여러 장이면 번호로 고르게 함 |
| 번호를 고르라는 질문에 다른 요청을 치면 같은 질문만 반복 | 번호가 아닌 답을 처리할 길이 없음 | LLM 없이 "현재 'OO' 업무 중입니다. '취소' 후 다시" 를 붙여 다시 묻기. 부족 정보 질문은 extract 가 다른 요청인지 알아채 멈춤 |
| 예약이 입력할 때만 실행됨 | 입력을 기다리는 동안 아무것도 돌지 않음 | 30초 스케줄러 스레드. 화면이 섞이지 않게 결과는 큐에 모아 입력 사이에 보여주고, 파일을 동시에 쓰지 않게 잠금 하나로 입력 처리와 스케줄러를 나눔 |
| "아까 이체 됐어?" 에 예약 이체 결과가 안 나옴 | 예약 실행이 처리 기록(requests)을 남기지 않음 | 예약·분할 회차 실행도 처리 기록을 남기게 함. 결과 조회는 LLM 기억이 아니라 이 원장에서 답함 |
| 분할 결제 중 일부만 내면 회차 금액과 남은 금액이 어긋남 | 분할 계획이 남은 금액과 따로 움직임 | 분할 중에는 남은 금액을 한 번에 다 낼 때(중도 상환)만 받음 |
| 비밀번호가 data.json 에 평문, 화면에도 보임 | 가상 데이터라도 실제 앱과 같은 습관이 필요 | pbkdf2 해시(salt, 10만 번)로 저장·비교, 입력은 `getpass`, 로그는 `****` |
| 로그가 너무 길어 문제 턴을 찾기 어려움 | 모든 턴을 펼쳐 씀 | 잘 끝난 턴은 한 줄 요약, 실패·예외 턴만 펼침. 스케줄러는 실행한 게 있을 때만 |
| 파일이 너무 길어짐 (이체 노드 350줄, functions.py 700줄) | 노드 안에 계산이 쌓임 | 계산은 `functions/` 업무별 파일로, 에이전트는 층별 폴더로 나눔 |
| 확인 스크립트 결과가 헷갈림 | 한 세션에 요청을 연달아 넣어, 멈춘 업무 뒤에 앞 요청 결과가 찍힘 | 요청마다 새 thread 로 부르고, 멈추면 "(여기서 멈춤)" 과 멈춘 질문을 보여줌 |

## 3. 남은 한계와 개선하고 싶은 점

| 한계 | 개선 방향 |
|---|---|
| 새 요청마다 LLM 을 최대 4번 차례로 부름 (rewrite → supervisor → router → extract). 응답이 몇 초씩 걸림 | 1단·2단 분류를 한 번에 하거나, 짧은 요청은 규칙으로 먼저 거르기 |
| 체크포인터가 메모리(`InMemorySaver`)라 끄면 멈춘 업무의 State 가 사라짐. 재시작 복구는 첫 문장으로 처음부터 다시 | SQLite 체크포인터로 바꾸면 멈춘 자리에서 이어갈 수 있음 (승인은 다시 받기) |
| 로그인 기능이 없고 사용자가 한 명(user-001)으로 고정 | 로그인 후 owner_id 를 세션에 두기 |
| 대화 기억은 세션 동안만, 장기 기억(자주 쓰는 배송지·결제 계좌) 없음 | LangGraph Store 로 사용자별 선호 저장 |
| 확인 스크립트가 결과를 출력만 하고 사람이 눈으로 확인 | 기대값을 assert 로 적은 자동 테스트(pytest). LLM 부분은 가짜 LLM 으로 |
| 처리안에서 나눠 이체의 한 줄을 빼는 수정("여행 자금은 빼줘")은 받지 않음 | 수정 때 목록에서 줄을 빼는 경우도 받기 |
| 다른 은행으로 보낸 출금 내역에 받는 사람이 적히지 않음 | 거래 내역에 받는 계좌(등록 ID·별명)도 적기 |
| 긴 함수 (`setting_check_node` 82줄, 할 일 4가지) | 기능을 더 붙일 때 할 일별 함수로 나누기 |
