virtual-bank-agent 설계 기획서 (최종본)

구현을 마친 뒤 실제 코드에 맞춰 고친 설계다.
그림은 그래프/ 폴더 (.mmd 원본, .png 사진), 표로 정리한 판은 최종_설계.md 에 있다.
초안 : ../설계 초안/기획서_수기(초안).txt
설계 중 : ../설계 중/기획서_수기(정리).txt (원본 대조는 기획서_수기(진행).txt)


기본 설계 원칙
- supervisor 패턴으로 각 Agent로 나누어서 노드 및 그래프를 구현한다.
- 각 Agent는 compile한 subgraph를 상위 그래프의 노드로 등록한다. (3단 -> 2단 -> 1단)
 * tool로 감싸지 않는다. interrupt 재개 시 노드를 처음부터 다시 실행하므로
   tool로 감싸면 재실행 범위가 커져 부작용이 두 번 일어난다.
 * checkpointer는 맨 바깥 bank_graph 하나에만 두고 안쪽 그래프가 물려받는다.
- 데이터에 쓰기가 일어나는 모든 업무는 본인 확인 -> 처리안 -> 승인(HITL) 을 거친다.
 * 읽기만 하는 조회는 인증·승인 없이 바로 보여준다. (카드 번호 조회만 본인 확인)
- interrupt가 있는 노드에는 부작용을 두지 않는다.
 * propose(계산만) / common_approve(interrupt 한 줄) / execute(승인 뒤에만 변경) 로 나눈다.
- 공통 부분은 agent가 아니라 공통 노드로 만든다.
 * 모든 업무가 똑같이 거치는 단계만 공통으로 둔다. (인증, 승인, 해석, 거절, 기록, 저장, 안내, 카드 고르기)
- 성공 여부와 금액 등 수치는 functions 가 낸 값을 그대로 쓴다.
 * llm은 사용자 말에서 값을 뽑고 분류만 한다. 수치를 만들거나 결과 문장을 다시 쓰지 않는다.
- 노드는 흐름만, functions/ 는 계산만, data_store 는 파일 읽기·쓰기만 맡는다.
 * functions 의 변경 함수는 data 안에서만 바꾸고 저장하지 않는다. 저장은 common_save 한 곳.


폴더
src/main.py          입력 루프, 분기 0, 대화 기억, 재시작 복구, 30초 스케줄러
src/state.py         BankState 하나를 모든 그래프가 같이 쓴다
src/model.py         llm (gemini) 한 곳에서 만든다
src/data_store.py    data.json 읽기·저장 (임시 파일에 쓰고 이름만 바꾸는 원자적 저장, 원본 보호)
src/logger.py        턴 단위 실행 로그 (logs/날짜.log)
src/functions/       common / account / transfer / card / reissue / billing
src/agents/          supervisor(1단) / account(2단) -> transfer, setting(3단)
                     card(2단) -> setting, reissue, billing(3단) / result / common
* 에이전트 폴더마다 graph.py(연결) / nodes.py(노드) / prompts.py(프롬프트)


흐름 (입력 한 번)
입력(자연어)
-> [분기 0] 멈춰 있는 업무가 있는가 (common_pending_check)
 -> 승인 대기 / 질문 대기 : 입력을 그 답으로 넘겨 멈춘 노드부터 다시 실행
 -> 없음 : new_request 로 이번 업무 칸을 비우고 새 요청으로 시작
-> (처리 전에 시각이 지난 예약 이체·분할 회차를 먼저 실행)
-> rewrite : 최근 대화를 보고 "그 카드" -> "여행 카드" 처럼 가리키는 말을 이름으로
-> supervisor (1단 분류 : 계좌 / 카드 / 결과 / 없음)
-> 도메인 Agent (2단 분류)
 * 내 도메인이 아니면 반대쪽으로 반송 (1회까지)
-> 기능 Agent (3단)
 -> extract : llm 으로 할 일과 필요한 값을 뽑는다 (비어 있는 칸만 채운다)
 -> check : 이름을 ID 로 바꾸고 할 수 있는지 본다
   -> 사유 있음 : fail -> 사유 안내 후 종료
   -> 후보 여러 개 : 번호로 고르기 (interrupt) -> check 로 복귀
   -> 빠진 값 : 질문 (interrupt) -> 답으로 extract 복귀
   -> 다 모임 : 본인 확인 (세션 1회, interrupt)
     -> 처리안 제시 -> 승인 요청 (interrupt) -> 답 해석 (llm)
        -> 승인 : 실행 직전 재검사 -> 실행 -> 처리 기록 -> 저장 -> 안내
        -> 거절·취소·다른요청 : 변경 없이 거절 기록 -> 종료
        -> 수정 : 바뀐 칸만 덮어쓰고 check 부터 다시 -> 처리안 다시 제시
        -> 모름 : 같은 처리안으로 다시 묻기
        -> 저장 실패 (3회) : 변경 전 상태 유지 후 사유 안내
-> 그래프가 멈췄으면 질문·처리안을 보여주고 진행 중 업무를 data.json pending 에 적는다
-> 끝났으면 답을 보여주고 최근 대화에 한 줄 남긴다 (최근 5턴)
* 켜 있는 동안 스케줄러 스레드가 30초마다 예약 이체·분할 회차를 확인한다.
  결과는 outbox 에 모아 두었다가 다음 입력 때 보여준다. 파일은 work_lock 으로 한쪽만 쓴다.


분기 조건 (조회·변경·승인·거절·실패)
- 조회 : 할 일이 읽기 (조회, 거래내역, 목록, 요금 조회, 명세서) -> 바로 답하고 끝
- 변경 : 할 일이 쓰기 -> 인증 -> 처리안 -> 승인
- 승인 : common_interpret 가 "승인" -> execute
- 거절 : "거절" / "취소" / "다른요청" -> common_reject (저장 없음, 처리 기록만 거절로)
- 실패
 * check 의 사유 (잔액 부족, 없는 계좌·카드, 상태 전이 불가, 이미 납부 …)
 * 질문·번호 고르기·본인 확인에서 취소, 본인 확인 3회 실패
 * 실행 직전 재검사 실패 (승인 뒤 잔액이 바뀜)
 * 저장 3회 실패


1. 1단 : bank_graph (agents/supervisor)
** 노드
- rewrite : 가리키는 말을 이름으로 (최근 대화가 있을 때만 llm)
- supervisor : 분야 고르기 (llm)
- account / card : 2단 그래프
- result : 처리 기록(requests)에서 찾아 답 ("아까 이체 됐어?")
- guide : 은행 업무가 아니면 사용법 안내
- bounce / bounce_fail : 도메인 반송 1회 / 두 번째면 안내
** 연결
START -> rewrite -> supervisor
supervisor -> 계좌 : account / 카드 : card / 결과 : result / 없음 : guide
account -> task=카드 업무 : 반송 전이면 bounce, 이미 반송했으면 bounce_fail / 그 밖 : END
card    -> task=계좌 업무 : 반송 전이면 bounce, 이미 반송했으면 bounce_fail / 그 밖 : END
bounce -> 반대쪽 (card 또는 account)
result, guide, bounce_fail -> END


2. 계좌
* 2단 : account_graph (agents/account)
** 연결
START -> account_router (llm)
account_router -> 조회 : account_query (목록·잔액·총액)
               -> 거래내역 : account_history (기간·계좌·종류·금액 조건 조합)
               -> 이체 : transfer (3단)
               -> 설정 : account_setting (3단)
               -> 카드 업무 : END (반송)
** 규칙
- 기준일은 오늘. 이번 주 = 월~일, 이번 달 = 오늘이 속한 달, 시작일·종료일 포함
- 최근순. 카드 결제 건은 사용한 카드도 표시. 합계는 Python 이 더한다


* 3단 : 이체 transfer_graph (agents/account/transfer)
** state
- from_name, to_name : 사용자가 말한 이름
- from_account, to_account : 찾아낸 ID (to 는 내 계좌 acc- 또는 등록 계좌 reg-)
- amount : 금액 / keep_amount : 남길 금액 (조건부)
- splits : 나눠 이체 [{to_name, amount, to_account}] / split_index : 지금 묻는 줄
- targets : 실제로 보낼 목록 [{to_account, to_name, amount}]
- scheduled_at : 예약 시각
- candidates, confirm_for, pick_warning, question, error
- proposal, approval, new_data, result
- last_transfer : 직전 이체 (새 요청에도 남긴다)
** 연결
START -> transfer_extract (llm) -> transfer_check
transfer_check -> error : transfer_fail
               -> 후보 여러 개 : transfer_confirm (번호 고르기) -> check
               -> 출금 계좌나 목록이 모자람 : transfer_ask (질문) -> extract
               -> 다 모임 : common_authenticate
common_authenticate -> 틀림 : 다시 / 취소·3회 실패 : fail / 인증됨 : transfer_propose
transfer_propose -> common_approve -> common_interpret
common_interpret -> 승인 : transfer_execute / 거절·취소·다른요청 : common_reject
                 -> 수정 : transfer_revise -> check / 모름 : common_approve
transfer_execute, common_reject -> common_log_request -> common_save -> common_report -> END
* 유형은 따로 분류하지 않는다. keep_amount 가 있으면 조건부, splits 가 2줄 이상이면 나눠, scheduled_at 이 있으면 예약.
** 분기 조건
- 계좌 이름에 맞는 게 없음 -> 불가 / 여러 개 -> 번호로 고르기
- 출금 계좌 == 입금 계좌 (등록 계좌가 내 계좌를 가리키는 경우 포함) -> 불가
- 이체 금액 0 이하 / 남길 금액 0 미만 / 남기면 보낼 금액이 없음 -> 불가
- 잔액 < 총액 -> 불가
- 예약 시각이 지남 -> 불가 / 예약인데 조건부·나눠 -> "한 곳씩 따로 예약" 안내
- 실행 직전 : 조건부인데 잔액이 바뀌어 금액이 달라짐 -> 실행하지 않고 다시 요청 안내
** 처리 규칙
- 이체하면 거래 내역에 출금 1건 + 입금 1건. 다른 은행 등록 계좌면 출금 1건만
- 나눠 이체는 전부 아니면 전무. 총액을 먼저 보고, 한 번에 저장한다
- 예약은 돈을 옮기지 않고 scheduled_transfers 에 남긴다 (상태 예약 -> 완료 / 실패 / 취소)
- 예약 실행은 켤 때, 입력할 때, 30초 스케줄러가 한다. 잔액이 모자라면 실패로 남긴다. 처리 기록에도 남긴다


* 3단 : 계좌 설정 setting_graph (agents/account/setting)
** 할 일
- 변경 (별명 / 용도) / 등록 (상대 계좌 주소록) / 삭제 / 조회 / 예약조회 / 예약취소
** 연결
START -> setting_extract (llm)
setting_extract -> 조회·예약조회 : setting_list -> END
                -> 그 밖 : setting_check
setting_check -> error : setting_fail
              -> 후보 여러 개 : setting_confirm -> check
              -> 빠진 값(question) : setting_ask -> extract
              -> 다 모임 : common_authenticate -> setting_propose
common_interpret -> 승인 : setting_execute / 거절 : common_reject / 수정 : setting_extract / 모름 : common_approve
setting_execute, common_reject -> common_log_request -> common_save -> common_report -> END
** 분기 조건
- 별명·용도는 앞뒤 공백을 뗀 1~20자, 지금 값과 같으면 불가
- 별명은 내 다른 계좌와 겹치면 불가, 용도는 겹쳐도 된다
- 등록은 은행·계좌번호·예금주가 다 있어야 한다 (빠지면 그 칸만 질문), 이미 등록한 계좌번호면 불가
- 별명을 안 말하면 예금주 이름으로


3. 카드
* 2단 : card_graph (agents/card)
** 연결
START -> card_router (llm)
card_router -> 조회 : card_extract (llm)
            -> 설정 : card_setting (3단)
            -> 재발급 : reissue (3단)
            -> 결제 : billing (3단)
            -> 계좌 업무 : END (반송)
card_extract -> 카드 번호 : common_authenticate -> card_query
             -> 그 밖 : card_query -> END
card_setting -> 분실 신고 완료 + 재발급도 원함 : card_to_reissue -> reissue
             -> 그 밖 : END
** 조회 규칙
- 볼 것 : 목록 / 결제 계좌 / 카드 번호 / 멤버십 / 이용 내역
- 목록에는 상태를 꼭 보여준다. 사용 가능이 아니면 "(사용 불가)"
- 은행을 여러 곳 말하면 은행마다 나눠 보여준다. "OO은행 말고" 는 그 은행을 빼고 은행별로
- 카드 번호는 본인 확인 뒤 가리지 않고 전체
- 이용 내역 = 체크카드는 transactions(card_id), 신용카드는 card_usages 를 합쳐 최근순


* 3단 : 카드 설정 card_setting_graph (agents/card/setting)
** 할 일
- 분실 신고 / 일시 잠금 / 잠금 해제 / 해지 / 별칭 변경 / 비밀번호 변경 / 등록
** 연결
START -> card_setting_extract (llm) -> card_setting_check
card_setting_check -> error : card_setting_fail
                   -> 카드 여러 장 : common_pick_card -> check
                   -> 정해짐 : common_authenticate
common_authenticate -> 비밀번호 변경이고 새 비밀번호가 없음 : card_setting_password (가린 입력) -> propose
                    -> 그 밖 : card_setting_propose
common_interpret -> 승인 : card_setting_execute / 거절 : common_reject / 수정 : extract / 모름 : common_approve
** 상태 전이
active(사용 가능) -> locked(일시 잠금) / lost(분실 정지) / cancelled(해지)
locked -> active(잠금 해제) / lost / cancelled
lost -> cancelled 만 (잠금·해제 불가. 재발급을 안내)
cancelled -> 아무것도 안 됨
이미 같은 상태면 불가
- 분실·도난·부정사용은 모두 lost, 사유(report_reason)와 신고 시각만 따로
- 해지는 지우지 않고 cancelled 로 둔다 (이용 내역이 참조를 잃지 않게)
- 카드 이름은 정확히 같은 이름을 먼저 보고, 없을 때만 글자가 들어간 카드를 찾는다
- 새 비밀번호는 숫자 4자리, 지금과 달라야 한다. llm 을 거치지 않고 해시로 저장


* 3단 : 재발급 reissue_graph (agents/card/reissue)
** 할 일
- 신청 / 조회 / 배송지 수정 / 신청 취소
** 연결
START -> 분실 신고에서 이어 옴(reissue_next) : reissue_check / 그 밖 : reissue_extract (llm)
reissue_extract -> 조회 : reissue_list -> END / 그 밖 : reissue_check
reissue_check -> error : reissue_fail / 카드 여러 장 : common_pick_card -> check / 정해짐 : common_authenticate
common_authenticate -> reissue_propose -> common_approve -> common_interpret
common_interpret -> 승인 : reissue_execute / 거절 : common_reject / 수정 : extract / 모름 : common_approve
** 신청 상태
received(접수) -> making(제작중) -> shipping(배송중), 접수 상태에서만 cancelled(취소됨)
** 분기 조건
- 신청은 lost 카드만. 취소되지 않은 신청이 있으면 새로 만들지 않고 그 신청을 안내
- 배송지는 집 / 회사 중 하나로 정해져야 한다 (아니면 등록된 배송지를 안내)
- 배송지 수정·취소는 접수 상태일 때만. 지금 배송지와 같으면 불가
- 신청해도 기존 카드의 분실 정지는 그대로
** 정지 후 재발급
card_setting (분실 신고) -> 승인 1 -> 저장 -> card_to_reissue -> reissue (재발급 신청) -> 승인 2 -> 저장
* 승인을 따로 받는다. 2번째를 거절하거나 실패해도 분실 신고는 되돌리지 않는다.


* 3단 : 카드 요금 billing_graph (agents/card/billing)
** 할 일
- 요금 조회 / 명세서 조회 / 결제 (전체 / 부분 / 분할 / 일괄)
** 연결
START -> billing_extract (llm)
billing_extract -> error : billing_fail / 요금 조회 : billing_fee / 명세서 조회 : billing_statement / 결제 : billing_check
billing_check -> error : billing_fail / 정해짐 : common_authenticate -> billing_propose
common_interpret -> 승인 : billing_execute / 거절 : common_reject / 수정 : extract / 모름 : common_approve
** 규칙
- 청구서는 신용카드만. 청구 상태 unpaid(미납) / partial(일부 납부) / paid(납부 완료)
- 방식을 안 말하면 : 개월 수가 있으면 분할, 금액이 있으면 부분, 둘 다 없으면 전체
- 일괄이 아니면 낼 청구서가 하나여야 한다 (여러 건이면 목록을 보여주고 다시 요청)
- 계좌를 안 말하면 카드의 결제 계좌
- 전체·부분·분할 : 한 번에 저장, 실패하면 전부 롤백
- 일괄 : 건마다 내고 바로 저장. 중간에 실패해도 앞 건은 유지. 완료 / 실패 / 미처리로 안내
  * 나눠 이체(전부 아니면 전무)와 반대
- 분할 : 2~12개월. 첫 회차는 지금 내고, 남은 회차는 next_due_at(한 달 뒤)이 지나면 스케줄러가 낸다
  * 잔액이 모자라면 실패로 기록하고 하루 뒤 다시. 마지막 회차는 남은 금액 그대로
  * 분할 중인 청구서는 남은 금액을 한 번에 다 낼 때만 결제 (중도 상환하면 분할도 끝)
- 남은 금액보다 많이 / 0원 이하 / 잔액 부족 / 이미 납부 -> 불가


4. 후속 결과 조회 (agents/result)
- llm 이 업무 키워드, 기간, 대상 이름, 여러 건 여부를 뽑는다
- functions.find_requests 가 처리 기록(requests)에서 조건으로 걸러 최근순
- 한 건만 물으면 가장 최근 기록, "다 보여줘" 면 최근 5건
* 답은 llm 기억이 아니라 파일에 남은 처리 기록에서 낸다. 인증·승인 없이 끝난다.


5. 공통 (agents/common)
** 노드
- common_pending_check : 분기 0. 멈춘 업무의 종류 (승인 / 질문 / 비밀 질문 / 없음)
- common_pick_card : 카드가 여러 장이면 번호로 고르기
- common_authenticate : 본인 확인 (계좌 비밀번호 / PIN / 휴대전화번호 / 주민번호 뒷자리 중 하나)
 * 세션 동안 한 번. 처리안 전에 받는다. 3번 틀리면 처음부터 다시
- common_approve : 처리안을 보여주고 interrupt 한 줄만
- common_interpret : 답을 승인 / 거절 / 취소 / 수정 / 다른요청 / 모름 으로 (llm)
 * 모르는 답은 승인으로 보지 않는다
- common_reject : 거절·취소 안내
- common_log_request : 처리 기록 한 줄 (처리안 표를 그대로 content 로)
- common_save : 저장, 실패하면 3번까지. 진행 중 업무(pending)도 같은 저장에서 지운다
- common_report : 저장이 실패했을 때만 실패 안내로 바꾼다
 * 저장과 안내를 나눈 이유 : 한 곳에 두면 저장이 실패했는데 "완료" 를 말하게 된다
** 되묻기 공통 규칙
- 질문·번호 고르기·본인 확인에 "취소", "그만", "안 할래", "됐어" 를 치면 그 업무를 그만둔다
- 질문에 다른 요청을 치면 extract 가 알아채 지금 업무를 멈추고 다시 입력하게 한다
- 번호 고르기에 번호가 아닌 말을 치면 llm 없이 "현재 'OO' 업무 중입니다. '취소' 후 다시" 를 붙여 다시 묻는다
** 재시작 복구
- 멈춘 채 턴이 끝나면 data.json pending 에 원래 요청 문장·업무·종류·시각을 적는다
- 켤 때 남아 있으면 알려주고 다시 할지 묻는다. 다시 하면 원래 문장으로 처음부터 (잔액·상태 다시 검사, 승인도 다시)
- 이전 승인만으로 자동 실행하지 않는다
** 보안
- 계좌 비밀번호 / PIN / 주민번호 뒷자리 / 카드 비밀번호는 pbkdf2 해시(salt, 10만 번)로 저장·비교
- 비밀번호를 묻는 중에는 터미널 입력을 가린다 (getpass). 로그에는 **** 로
** 로그
- 턴 단위로 모았다가 한 번에 쓴다. 잘 끝난 턴은 한 줄 요약, 실패·예외 턴만 펼친다
- 라우팅(1단·2단 선택과 근거), 노드와 소요 시간, 이름 해소, 파일 읽기·쓰기, interrupt, 예외
- 스케줄러는 실제로 실행한 게 있을 때만 남긴다. --debug 면 콘솔에도


6. State (BankState) 변경 시점
- 새 요청 : new_request 가 이번 업무 칸을 모두 비운다. last_transfer, authenticated 만 남긴다
- query : 입력 -> rewrite(바꾼 문장) -> 질문 노드(답) -> common_approve(승인 질문의 답)
- request_text : 처음 문장 (rewrite 가 바꾸면 바꾼 문장). 재시작 복구에 쓴다
- domain / reason : supervisor, bounce / task : 2단 router / bounced : bounce
- 이체 칸 : extract 가 비어 있는 칸만, check 가 ID·targets, confirm 이 고른 ID, revise 가 바뀐 칸
- 설정 칸(setting_action, target_name, new_value, reg_info) : 각 extract / target_account : check·confirm
- card_filter : card_extract / address_id : reissue_check / billing_info : billing_extract·billing_check
- reissue_next, reissue_address : card_setting_extract / card_to_reissue 가 재발급용으로 바꾼다
- candidates, pick_warning, question, error : check·고르기·질문 노드
- proposal / approval : propose(대기) -> common_interpret(결정)
- new_data : execute -> common_log_request -> common_save 가 저장 후 비운다
- result : execute(완료) / common_reject(거절) / common_save(실패)
- auth_tries, authenticated : common_authenticate
* 최근 대화는 main.py, 진행 중 업무는 data.json pending, 처리 기록은 data.json requests 에 둔다.
  체크포인터는 메모리라 끄면 사라지기 때문이다.


7. 초안에서 바뀐 것
초안 -> 설계 중 (구현 전 검토)
1. 분기 조건 / 처리 규칙 / 상태 전이 섹션을 새로 넣었다
 -> 기능 목록만으로는 언제 실패하고 언제 되돌아가는지 적을 자리가 없었다
2. HITL 기준을 "민감정보·돈" 에서 "파일을 바꾸는가" 로
 -> 분실 정지는 돈이 안 움직이고 별명 변경은 민감정보가 아니지만 둘 다 승인 대상이다
3. 승인 대기 판정(분기 0)을 맨 앞에 넣었다
 -> 없으면 "응, 진행해" 가 새 요청으로 분류된다
4. 승인을 부작용 없는 단독 노드로 분리했다 (propose / approve / execute)
 -> 재개하면 노드를 처음부터 다시 실행해 저장이 두 번 된다
5. 서브그래프를 tool 이 아니라 노드로 넣었다
6. 필요 정보 확인을 2단에서 3단으로 내렸다
 -> 2단에서는 유형을 몰라 무엇이 부족한지 알 수 없다
7. 도메인 반송 경로를 넣었다
8. 흐름에 되돌아오는 경로(질문, 수정, 거절)를 넣었다
9. 카드 에이전트를 2개에서 4개로 나눴다 (조회, 설정, 재발급, 결제)
10. 카드 상태와 재발급 신청 상태를 정의했다
11. 마지막 "llm 최종 검토 후 출력" 을 뺐다
 -> 금액·성공 여부를 llm 이 다시 쓰면 틀릴 수 있다
12. 설계 순서를 기능 단위 관통으로 바꿨다
13. 데이터 구조를 기능에 맞게 늘렸다

설계 중 -> 최종 구현
1. 공통 노드 17개 계획 -> 8개
 -> 무엇이 부족한지, 무엇을 물을지, 처리안에 무엇을 보일지가 업무마다 달라서
    업무별 노드(extract / check / confirm / ask / propose / revise / execute / fail)와 functions 로 나눴다
2. 대상 해소 노드 -> functions.find_* 함수 (이름 -> ID 는 계산이라서)
3. transfer_router(유형 분류) -> 없앰. extract 가 뽑은 값으로 유형이 정해진다
 -> 한 요청이 조건부 + 예약처럼 여러 축을 같이 가져 하나로 분류할 수 없다. llm 호출도 한 번 준다
4. 재검증 노드 -> 실행 함수(transfer_all, check_payment) 바로 앞의 재검사
 -> 실행과 같은 데이터로 바로 앞에서 해야 사이에 바뀔 틈이 없다
5. 1단 계좌 / 카드 -> 계좌 / 카드 / 결과 / 없음, 앞에 rewrite
 -> 후속 결과 조회는 어느 도메인도 아니고, 은행 업무가 아닌 말은 안내로 끝내야 했다
6. 맥락 확인 노드 -> main 이 최근 5턴을 들고 rewrite 가 가리키는 말만 이름으로 바꾼다
 -> 뒤의 노드들은 대화 기록을 몰라도 된다
7. 이력 조회 -> result 도메인 + 처리 기록(requests) 원장
8. 재분류 -> bounce 1회 (llm 을 다시 부르지 않고 반대쪽으로)
9. 다음 업무 -> card_to_reissue (이어서 처리하는 업무가 정지 후 재발급 하나뿐)
10. 조회 3단 에이전트 -> 2단 안의 노드 (읽기는 노드 한두 개로 끝난다)
11. 예약 : 입력할 때 확인 -> + 30초 스케줄러, 잠금(work_lock), 출력 큐(outbox)
 -> 입력이 없으면 시각이 지나도 실행되지 않았다
12. 예약은 금액을 정한 한 곳 이체만
 -> 조건부는 실행 때 잔액으로 금액이 정해져 승인한 금액과 달라진다
13. 비밀번호 : 검증 후 폐기 -> pbkdf2 해시로 저장, 입력 가림
14. 재시작 복구 : 이어서 처리 -> pending 에 적고 켤 때 처음부터 다시 (승인도 다시)
15. 질문·번호 고르기 중 다른 요청 : other_request, pick_warning
16. 카드 이름 : 정확히 같은 이름 먼저, 여러 장이면 번호로 고르기
17. 카드 조회 : 은행별로 나눠, "OO은행 말고" 는 빼고
18. 분할 결제 : 남은 회차 자동 납부, 분할 중 부분 결제는 막음
19. 등록 계좌도 이체 입금 대상으로
20. 로그 : 잘 끝난 턴은 한 줄 요약, 실패한 턴만 펼침
21. 처리 기록 : 처리안 표를 그대로 content 로 (사용자가 본 내용과 같게)
22. 파일 구조 : agents 층별 폴더, functions 업무별 파일 (노드 350줄, functions 700줄까지 늘어서)
23. langsmith 를 쓰지 않고 파일 로그만 (분류 결과와 근거는 route 줄로 충분)


8. 하지 않은 것
- 재시작 복구에서 첫 문장 뒤의 답까지 복원하기 : 첫 문장으로만 다시 돌린다
- 카드 사용(가맹점 결제) : 범위 밖. 사용할 수 없다는 안내만
- 청구서(bills) 카테고리 : 카드 결제와 흐름이 같아 뺐다. 부분·일괄 결제는 카드로 옮겼다
- 장기 기억 (자주 쓰는 배송지·계좌) : 대화 기억은 세션 동안만
- 하위 그래프의 같은 모양 분기 함수 합치기 : 합치면 오히려 읽기 어렵다
- 긴 함수 나누기 (setting_check_node 82줄) : 기능을 더 붙일 때 나눈다
