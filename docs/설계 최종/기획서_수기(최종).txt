virtual_bank_agent 설계 기획서 (최종)

초안을 기준으로 실제 구현을 마친 뒤 바뀐 내용을 반영했다.
그림은 그래프/ 폴더에 있고, 표로 자세히 정리한 건 최종_설계.md 에 있다.


기본 설계 원칙
- supervisor 패턴으로 각 Agent로 나누어서 노드 및 그래프를 구현한다.
- 각 Agent는 subgraph로 만들어서 상위 그래프의 노드로 넣는다. (3단 -> 2단 -> 1단)
 * tool로 감싸지 않았다. interrupt로 멈췄다가 다시 시작하면 노드를 처음부터 다시 실행해서, tool로 감싸면 저장이 두 번 될 수 있다.
- 데이터가 바뀌는 업무는 모두 본인 확인 -> 처리안 -> 승인(Human in the Loop)을 거치고 실행한다.
 * 초안에서는 "민감정보, 돈과 관련된 것"만 승인을 받으려고 했는데, 분실 정지처럼 돈이 안 움직여도 승인이 필요해서 기준을 바꿨다.
 * 조회는 승인 없이 바로 보여준다. (카드 번호 조회만 본인 확인)
- 승인 받는 노드와 실제로 저장하는 노드를 나눈다.
 * 처리안(계산만) -> 승인(interrupt만) -> 실행(승인 뒤에만)
- 공통 부분은 agent가 아니라 공통 노드로 만든다.
- llm은 사용자 말에서 값을 뽑고 분류만 한다. 날짜, 시간, 금액 계산, 성공 여부는 python 함수가 한다.


폴더
- main.py : 입력 받기, 멈춘 업무 확인, 대화 기억, 재시작 복구, 30초 스케줄러
- state.py : 모든 그래프가 같이 쓰는 state
- data_store.py : data.json 읽기/저장
- logger.py : 실행 로그
- functions/ : 계산만 하는 함수 (계좌, 이체, 카드, 재발급, 결제, 공통)
- agents/ : 노드와 그래프 (supervisor, account, card, result, common)
 * 에이전트 폴더마다 graph.py(연결) / nodes.py(노드) / prompts.py(프롬프트)


흐름
입력(자연어)
-> 멈춰 있는 업무가 있는지 확인
 -> 있으면 : 입력을 그 답으로 넘겨서 멈춘 곳부터 다시 진행
 -> 없으면 : 이전 업무 값을 비우고 새 요청으로 시작
-> 최근 대화를 보고 "그 카드" 같은 말을 실제 이름으로 바꿈(rewrite)
-> supervisor (1단 : 계좌 / 카드 / 결과 조회 / 은행 업무 아님)
-> 계좌 or 카드 Agent (2단)
 * 내 업무가 아니면 반대쪽으로 한 번 넘긴다. 두 번째도 아니면 안내하고 끝
-> 기능 Agent (3단)
 -> 조회 : 바로 결과 보여주고 끝
 -> 변경 : 값 뽑기 -> 검사 -> 본인 확인 -> 처리안 -> 승인 -> 실행 -> 기록 -> 저장 -> 안내
* 초안에 있던 "마지막에 llm이 보기 좋은 말로 정리"는 뺐다. llm이 금액을 다시 쓰면 틀릴 수 있어서 python이 계산한 값을 그대로 보여준다.


변경 업무 공통 흐름 (3단)
- 값 뽑기(extract) : llm으로 필요한 값을 뽑는다
- 검사(check) : 이름을 ID로 바꾸고 할 수 있는지 본다
 -> 안 되면 : 이유 안내하고 끝(fail)
 -> 후보가 여러 개면 : 번호로 고르기 -> 다시 검사
 -> 빠진 값이 있으면 : 질문 -> 다시 값 뽑기
 -> 다 모이면 : 본인 확인 (한 번 하면 계속 유지, 3번 틀리면 끝)
- 처리안(propose) : 무엇을 할지 보여준다 (계산만)
- 승인(common_approve) : 사용자 답을 기다린다
- 답 해석(common_interpret) : llm으로 승인 / 거절 / 취소 / 수정 / 다른 요청 / 모름
 -> 승인 : 실행 직전에 한 번 더 검사하고 실행
 -> 거절, 취소, 다른 요청 : 실행하지 않고 거절로 기록
 -> 수정 : 바뀐 값만 고치고 다시 검사 -> 새 처리안
 -> 모름 : 다시 묻기
- 기록(common_log_request) -> 저장(common_save, 실패하면 3번까지) -> 안내(common_report)


1. 계좌
* 계좌 : account_graph (2단)
** 노드
- 요청 분류(account_router)
- 계좌 조회(account_query) : 목록, 잔액, 총액
- 거래 내역(account_history) : 기간, 계좌, 입금/출금, 금액으로 검색
- 이체(transfer) : 3단
- 설정(account_setting) : 3단
* 초안에서는 조회도 따로 agent(AccountQueryAgent)로 두려고 했는데, 조회는 승인이나 저장이 없어서 노드 하나로 끝냈다.


* 이체 : transfer_graph (3단)
** state
- 보내는 계좌 / 받는 계좌 (내 계좌 or 등록한 계좌)
- 이체 금액
- 남길 금액 (조건부 이체)
- 나눠 보낼 목록 (나눠 이체)
- 예약 시각 (예약 이체)
- 직전 이체 (다음 요청에도 남김)

** 노드
- 값 뽑기(transfer_extract)
- 검사(transfer_check)
- 번호 고르기(transfer_confirm)
- 부족한 정보 질문(transfer_ask)
- 처리안(transfer_propose)
- 수정(transfer_revise)
- 실행(transfer_execute)
- 실패 안내(transfer_fail)

** 기능
- 즉시 이체
- 조건부 이체 ("40만원 남기고 나머지")
- 나눠 이체 (여러 곳에 나눠 보내기)
- 예약 이체
* 초안에서는 이체 유형을 분류하는 노드(transfer_router)를 두려고 했는데, "40만원 남기고 내일 보내줘"처럼 여러 유형이 같이 와서 없앴다.
  뽑은 값이 있는지로 정한다. (남길 금액이 있으면 조건부, 목록이 2개 이상이면 나눠, 예약 시각이 있으면 예약)

** 안 되는 경우
- 계좌를 못 찾음 / 보내는 계좌와 받는 계좌가 같음
- 금액이 0 이하 / 잔액 부족
- 예약 시각이 이미 지남
- 조건부, 나눠 이체는 예약 불가 (조건부는 실행할 때 금액이 바뀔 수 있어서)
- 승인 뒤 실행 직전에 잔액이 바뀜

** 처리 규칙
- 나눠 이체는 하나라도 안 되면 전부 실행하지 않는다
- 예약 이체는 30초마다 스케줄러가 확인해서 시간이 되면 실행한다


* 설정 : setting_graph (3단)
** 기능
- 계좌 별명 / 용도 변경
- 상대 계좌 등록 / 삭제 / 조회 (주소록처럼 등록해서 이체할 때 사용)
- 예약 이체 조회 / 취소

** 안 되는 경우
- 별명, 용도가 비어 있거나 20자 넘음 / 지금과 같음
- 별명이 내 다른 계좌와 겹침
- 등록할 때 은행, 계좌번호, 예금주 중 빠진 게 있으면 그것만 다시 묻는다


2. 카드
* 카드 : card_graph (2단)
** 노드
- 요청 분류(card_router)
- 카드 조회(card_extract -> card_query)
- 설정(card_setting) : 3단
- 재발급(reissue) : 3단
- 결제(billing) : 3단
* 초안에서는 카드 agent를 조회/결제, 설정 2개로 나눴는데 한 agent에 기능이 너무 많아서 조회, 설정, 재발급, 결제 4개로 나눴다.

** 조회 기능
- 카드 목록 (은행별로, "OO은행 말고"도 가능)
- 결제 계좌 / 멤버십 / 이용 내역
- 카드 번호 (본인 확인 뒤에만)


* 설정 : card_setting_graph (3단)
** 기능
- 분실 신고
- 일시 잠금 / 잠금 해제
- 해지
- 별칭 변경
- 비밀번호 변경
- 카드 등록

** 카드 상태
- 사용 가능 -> 잠금 / 분실 정지 / 해지
- 잠금 -> 사용 가능(해제) / 분실 정지 / 해지
- 분실 정지 -> 해지만 가능 (해제 안 됨, 재발급 안내)
- 해지 -> 아무것도 안 됨

** 규칙
- 카드 이름이 똑같은 걸 먼저 찾고, 여러 장이 나오면 번호로 고르게 한다
- 새 비밀번호는 숫자 4자리, 지금이랑 달라야 한다


* 재발급 : reissue_graph (3단)
** 기능
- 재발급 신청 / 조회 / 배송지 수정 / 신청 취소

** 신청 상태
- 접수 -> 제작중 -> 배송중
- 접수일 때만 배송지 수정, 취소 가능

** 규칙
- 분실 정지된 카드만 신청 가능
- "분실했으니 정지하고 재발급해줘"는 승인을 두 번 따로 받는다
 * 분실 정지 승인 -> 저장 -> 재발급 승인 -> 저장
 * 재발급을 거절해도 분실 정지는 그대로 남는다


* 결제 : billing_graph (3단)
** 기능
- 요금 조회 / 명세서 조회
- 요금 결제 (전체 / 부분 / 분할 / 일괄)

** 규칙
- 신용카드만 청구서가 있다
- 분할은 2~12개월. 첫 회차는 바로 내고, 나머지는 한 달마다 스케줄러가 낸다
 * 잔액이 없으면 실패로 기록하고 하루 뒤 다시
- 분할 중에는 남은 금액을 한 번에 다 낼 때만 결제 가능
- 일괄 결제는 한 건씩 내고 바로 저장한다. 중간에 실패해도 앞에 낸 건은 남는다
- 남은 금액보다 많이 / 0원 이하 / 잔액 부족 / 이미 냄 -> 불가


3. 결과 조회 (result)
- "아까 이체 됐어?" 같은 질문에 답한다
- llm 기억이 아니라 data.json에 남은 처리 기록(requests)에서 찾아서 답한다
- 예약 이체, 분할 결제가 자동으로 실행된 것도 처리 기록에 남긴다


4. 공통 (common)
** 노드
- 멈춘 업무 확인(common_pending_check)
- 카드 번호로 고르기(common_pick_card)
- 본인 확인(common_authenticate)
- 승인 요청(common_approve)
- 답 해석(common_interpret)
- 거절(common_reject)
- 처리 기록(common_log_request)
- 저장(common_save)
- 결과 안내(common_report)
* 설계 중에는 공통 노드를 17개 정도 생각했는데, 업무마다 물어보는 게 달라서 결국 모든 업무가 똑같이 거치는 것만 공통으로 남겼다. (멈춘 업무 확인은 main.py가 입력마다 부른다)

** 되묻기 규칙
- 질문 중에 "취소", "그만" 등을 치면 그 업무를 그만둔다
- 질문 중에 다른 요청을 치면 지금 업무를 멈추고 다시 입력하라고 안내한다
- 번호 고르기에 번호가 아닌 걸 치면 "현재 OO 업무 중입니다. '취소' 후 다시" 안내

** 재시작 복구
- 승인이나 질문을 기다리는 중에 끄면 data.json의 pending에 저장한다
- 다시 켜면 멈춘 업무를 알려주고 처음부터 다시 진행한다 (승인도 다시 받음)

** 보안
- 비밀번호, PIN, 주민번호 뒷자리는 해시(pbkdf2)로 저장하고 비교한다
- 비밀번호 입력할 때 화면에 안 보이게 가리고, 로그에는 **** 로 남긴다

** 저장
- 임시 파일에 다 쓰고 바꿔 끼우는 방식(원자적 저장)
- 실패하면 3번까지 다시 시도, 끝까지 안 되면 원래 데이터 유지

** 스케줄러
- 30초마다 예약 이체, 분할 결제를 확인한다
- 결과는 큐에 모아 뒀다가 다음 입력 때 보여준다 (입력 중에 끼어들지 않게)
- 사용자 요청과 동시에 파일을 저장하지 않게 잠금을 건다 (threading.Lock)


5. state 에서 신경 쓴 것
- 새 요청이 오면 이전 업무 값을 전부 비운다 (전 요청 값이 섞이는 문제가 있었다)
- 본인 확인, 직전 이체만 다음 요청에도 남긴다
- 최근 대화 5턴은 main.py가 들고 있다
- 진행 중 업무는 data.json pending, 처리 기록은 data.json requests에 둔다
 * 체크포인터는 메모리라 프로그램을 끄면 사라져서


6. 초안에서 바뀐 것
- 승인 기준 : 민감정보, 돈 -> 데이터가 바뀌는지
- 맨 앞에 "멈춘 업무가 있는지" 확인하는 분기를 넣었다 (없으면 "응, 진행해"가 새 요청으로 분류됨)
- 승인 노드를 처리안 / 승인 / 실행으로 나눴다
- subgraph를 tool이 아니라 노드로 넣었다
- 부족한 정보 확인을 2단에서 3단으로 옮겼다 (2단에서는 뭐가 부족한지 모름)
- 잘못 분류했을 때 반대쪽으로 넘기는 경로를 넣었다
- 질문, 수정, 거절처럼 되돌아가는 흐름을 넣었다
- 카드 agent 2개 -> 4개
- 마지막 llm 최종 검토 단계를 뺐다
- 공통 노드 17개 -> 8개
- 이체 유형 분류 노드를 없앴다
- 1단에 결과 조회, 은행 업무 아님을 추가하고 앞에 rewrite를 넣었다
- 조회는 3단 agent 대신 2단 안의 노드로
- 예약 이체에 30초 스케줄러, 큐, 잠금 추가
- 비밀번호를 해시로 저장
- 재시작 복구는 이어서가 아니라 처음부터 다시
- 카드 이름은 똑같은 이름 먼저, 여러 장이면 번호로
- 분할 결제 남은 회차 자동 납부
- 등록한 계좌로도 이체 가능
- 파일이 너무 길어져서 agents/ 층별 폴더, functions/ 업무별 파일로 나눴다
- langsmith는 빼고 파일 로그만 썼다


7. 하지 않은 것
- 재시작할 때 첫 문장 뒤에 답한 것까지 복원하기 : 첫 문장으로 처음부터 다시 한다
- 카드로 가맹점 결제하기 : 범위 밖이라 안내만
- 장기 기억 (자주 쓰는 계좌, 배송지) : 대화 기억은 켜져 있는 동안만
- 비슷한 분기 함수 합치기 : 합치면 오히려 읽기 어려워서
- 긴 함수 나누기 : 기능을 더 붙일 때 나누기로 했다
