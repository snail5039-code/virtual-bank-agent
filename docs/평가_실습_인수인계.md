# LangGraph 평가 실습 인수인계

작성일: 2026-10-01

## 1. 실습 주제

어제 진행한 내용은 가상 은행 Agent를 단순 테스트 코드로 확인하는 단계에서, Golden Set 기반 평가 구조로 옮기는 작업이다.

평가 대상은 계좌 전체 기능 중 우선 계좌 조회, 이체, 조건부 이체, 예약 이체, 거래내역 조회 흐름이다.

핵심은 Agent 답변만 보는 것이 아니라 아래 3가지를 같이 평가하는 것이다.

1. 답변 평가
2. interrupt 흐름 평가
3. 데이터 상태 변화 평가

## 2. 참고한 노트북

원래 기준으로 삼은 파일:

```text
C:/puh/aim-ai-agent-my/langchain_/30-langgraph-evaluation.ipynb
```

이 노트북의 평가 구조를 우리 프로젝트에 맞게 바꾸는 중이다.

노트북 쪽 구조는 대략 다음 흐름이었다.

```python
run_agent(inputs)
evaluate_answer(inputs, outputs, reference_outputs)
evaluate_interrupts(inputs, outputs, reference_outputs)
evaluate_data(inputs, outputs, reference_outputs)
main()
```

여기서 우리 프로젝트는 단순 question/answer가 아니라 여러 턴 대화, interrupt, JSON 데이터 변화가 있어서 그대로 복붙하면 안 되고 프로젝트 구조에 맞게 바꿔야 한다.

## 3. 현재 만든 파일

현재 평가 관련 파일은 아래 2개다.

```text
evaluation/golden_set.py
evaluation/run_eval.py
```

`golden_set.py`에는 평가 케이스를 넣었고, `run_eval.py`에는 Agent 실행 함수와 평가 함수들을 만드는 중이다.

## 4. Golden Set의 의미

Golden Set은 정답 데이터 모음이다.

여기서 정답은 하나의 완성 문장만 뜻하지 않는다.

우리 프로젝트에서는 정답을 3개로 나눠서 본다.

```python
"reference": {
    "answer_criteria": "...",
    "expected_interrupts": [...],
    "expected_data": {...},
}
```

각 필드의 의미는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `answer_criteria` | Agent 답변이 만족해야 하는 기준 |
| `expected_interrupts` | 실행 중 발생해야 하는 interrupt 순서 |
| `expected_data` | 실행 후 JSON 데이터가 어떤 상태여야 하는지 |

## 5. Golden Set 전체 구조

현재 Golden Set 한 케이스의 구조는 다음과 같다.

```python
{
    "case_id": "transfer_approve",
    "inputs": {
        "turns": [
            "생활비에서 저축으로 10만원 보내줘",
            "1234",
            "승인",
        ],
    },
    "reference": {
        "answer_criteria": "생활비에서 저축으로 100,000원 이체 완료를 안내한다.",
        "expected_interrupts": ["secret", "approval"],
        "expected_data": {
            "accounts": {
                "acc-001": {"balance": 1331800},
                "acc-002": {"balance": 2380000},
            },
            "transactions_added": 2,
            "last_request": {
                "task_type": "이체",
                "status": "완료",
            },
        },
    },
}
```

## 6. case_id 정리

`case_id`는 함수명이 아니다.

평가 케이스를 구분하기 위한 이름이다.

예를 들어 아래처럼 쓴다.

```python
"case_id": "transfer_approve"
```

뜻은 "이 케이스는 이체를 승인하는 케이스"라는 식별자다.

나중에 전체 실행 결과 표를 만들 때 이 이름이 행 이름처럼 쓰인다.

## 7. inputs.turns 정리

`inputs["turns"]`는 사용자가 Agent와 주고받는 입력 순서다.

예를 들어 이체 승인은 한 번에 끝나지 않는다.

```python
[
    "생활비에서 저축으로 10만원 보내줘",
    "1234",
    "승인",
]
```

첫 번째 턴은 요청이고, 두 번째 턴은 비밀번호 또는 인증 응답이고, 세 번째 턴은 승인 응답이다.

그래서 `question` 하나가 아니라 `turns` 배열로 만들었다.

## 8. expected_interrupts 정리

`expected_interrupts`는 실행 중 Agent가 멈추고 사용자 입력을 기다려야 하는 지점을 적는다.

예시는 다음과 같다.

```python
"expected_interrupts": ["secret", "approval"]
```

뜻은 다음 순서다.

1. `secret`: 비밀번호, 인증번호 같은 민감 입력을 받아야 함
2. `approval`: 최종 실행 전 사용자 승인을 받아야 함

금액이 빠진 요청은 완료하면 안 되고 되물어야 하므로 다음처럼 잡았다.

```python
"expected_interrupts": ["question"]
```

## 9. expected_data 정리

`expected_data`는 실행 후 JSON 데이터가 맞게 바뀌었는지 보는 기준이다.

이 필드 안의 이름들은 LangGraph가 정해준 예약어가 아니다.

우리가 평가 러너에서 알아보기 위해 정한 약속이다.

현재 쓰는 키는 다음과 같다.

| 키 | 의미 |
|---|---|
| `changed` | 데이터가 바뀌었는지 여부 |
| `accounts` | 특정 계좌의 최종 잔액 |
| `transactions_added` | 추가된 거래내역 개수 |
| `schedules_added` | 추가된 예약이체 개수 |
| `last_schedule` | 마지막 예약이체 내용 |
| `last_request` | 마지막 처리 요청 기록 |

중요한 점은 `expected_data`에 쓴 이름과 `evaluate_data()`에서 읽는 이름이 반드시 같아야 한다는 것이다.

## 12. run_agent의 역할

`run_agent()`는 평가 대상 Agent를 실제로 한 번 실행하는 함수다.

역할은 다음과 같다.

1. 새 `thread_id`를 만든다.
2. 데이터를 초기값으로 리셋한다.
3. 실행 전 데이터를 `before`로 저장한다.
4. 첫 사용자 입력으로 그래프를 실행한다.
5. interrupt가 나오면 다음 turn을 넣어서 resume한다.
6. 실행 후 데이터를 `after`로 저장한다.
7. 답변, interrupt 흐름, before/after 데이터를 반환한다.

즉 `run_agent()`는 평가 함수가 아니라 평가할 재료를 모으는 실행기다.

## 13. run_agent 반환값

현재 목표 반환값은 다음 구조다.

```python
return {
    "answer": "...",
    "interrupts": ["secret", "approval"],
    "used_turns": [...],
    "pending": False,
    "before": before,
    "after": after,
}
```

각 필드의 의미는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `answer` | Agent의 최종 답변 |
| `interrupts` | 실제 발생한 interrupt 종류 순서 |
| `used_turns` | 실제 사용한 사용자 입력 |
| `pending` | 아직 interrupt가 남아 있는지 |
| `before` | 실행 전 JSON 데이터 |
| `after` | 실행 후 JSON 데이터 |

## 14. 현재 run_eval.py에서 바로 고쳐야 할 점

현재 `evaluation/run_eval.py`는 작성 중인 상태라 그대로 실행하면 오류가 날 가능성이 높다.

다음 세션에서 먼저 볼 부분은 아래다.

### 14-1. import 누락 확인

현재 코드에서 아래 이름들을 쓰고 있다.

```python
ROOT
json
uuid4
shutil
data_store
```

그런데 파일 상단에 import가 충분히 들어갔는지 확인해야 한다.

필요한 형태는 대략 다음과 같다.

```python
import json
import shutil
from pathlib import Path
from uuid import uuid4

from src import data_store
```

프로젝트 실행 방식에 따라 `src` 경로를 `sys.path`에 추가해야 할 수도 있다.

### 14-2. interrupt_seen 타입 오류

현재 코드에는 아래처럼 되어 있다.

```python
interrupt_seen = {}
```

그런데 아래에서 `.append()`를 쓰고 있다.

```python
interrupt_seen.append(item.value["kind"])
```

딕셔너리는 `.append()`가 없으므로 리스트로 바꿔야 한다.

```python
interrupt_seen = []
```

### 14-3. result["answer"] 확인

현재 마지막 답변을 꺼낼 때 다음처럼 되어 있다.

```python
result["answer"]
```

하지만 실제 그래프 반환 구조가 `answer`인지, `messages`인지 확인해야 한다.

기존 노트북 예시는 보통 다음처럼 마지막 메시지에서 꺼냈다.

```python
result["messages"][-1].text
```

우리 그래프가 어떤 키를 반환하는지 한 케이스를 직접 찍어서 확인해야 한다.

## 15. evaluate_answer 정리

답변 평가는 LLM Judge로 한다.

현재 방향은 아래처럼 잡았다.

```python
def evaluate_answer(inputs, outputs, reference_outputs):
    return answer_judge(
        inputs=inputs["turns"][0],
        outputs=outputs["answer"],
        reference_outputs=reference_outputs["answer_criteria"],
    )
```

여기서 의미는 다음과 같다.

| 값 | 의미 |
|---|---|
| `inputs["turns"][0]` | 사용자의 첫 요청 |
| `outputs["answer"]` | Agent의 실제 답변 |
| `reference_outputs["answer_criteria"]` | Golden Set의 기대 답변 기준 |

이 함수는 문자열 완전 일치가 아니라, 기준을 만족하는지 LLM에게 판단시키는 방식이다.

## 16. evaluate_interrupts 정리

interrupt 평가는 LLM이 필요 없다.

리스트가 정확히 같은지 보면 된다.

```python
def evaluate_interrupts(inputs, outputs, reference_outputs):
    expected = reference_outputs["expected_interrupts"]
    actual = outputs["interrupts"]
    passed = actual == expected

    return {
        "key": "interrupt_flow",
        "score": passed,
        "comment": f"기대 interrupt: {expected}, 실제 interrupt: {actual}",
    }
```

여기서 중요한 점은 순서까지 본다는 것이다.

예를 들어 기대값이 다음과 같다면,

```python
["secret", "approval"]
```

실제값이 아래처럼 나오면 실패다.

```python
["approval", "secret"]
```

둘 다 들어 있더라도 흐름이 다르기 때문이다.

## 17. evaluate_data 정리

데이터 평가는 우리 프로젝트 전용으로 직접 만들어야 한다.

이유는 JSON 구조가 프로젝트마다 다르기 때문이다.

현재 방향은 다음과 같다.

1. `before = outputs["before"]`
2. `after = outputs["after"]`
3. `expected = reference_outputs["expected_data"]`
4. `expected` 안에 있는 키만 골라서 검사한다.

예를 들어 `changed`만 있으면 전체 데이터가 바뀌지 않았는지만 본다.

```python
"expected_data": {
    "changed": False,
}
```

`accounts`가 있으면 특정 계좌 잔액만 본다.

```python
"accounts": {
    "acc-001": {"balance": 1331800},
    "acc-002": {"balance": 2380000},
}
```

`transactions_added`가 있으면 거래내역이 몇 건 늘었는지 본다.

```python
"transactions_added": 2
```

## 18. 예약 이체 케이스 주의점

예약 이체는 즉시 이체와 다르다.

현재 Golden Set의 `scheduled_transfer`는 다음 기준으로 정했다.

```python
"accounts": {
    "acc-001": {"balance": 1431800},
    "acc-002": {"balance": 2280000},
},
"transactions_added": 0,
"schedules_added": 1,
"last_schedule": {
    "from_account": "acc-001",
    "to_account": "acc-002",
    "amount": 100000,
    "status": "예약",
},
```

즉 예약만 등록하고 실제 잔액은 즉시 바꾸지 않는다는 기준이다.

다음 세션에서 실제 구현이 이 기준과 맞는지 확인해야 한다.

## 19. 다음 세션에서 해야 할 일

다음 세션 첫 작업 순서는 이렇게 가면 된다.

1. `evaluation/run_eval.py` 실행 가능하게 import와 경로를 정리한다.
2. `interrupt_seen = {}`를 `interrupt_seen = []`로 수정한다.
3. 그래프 반환 구조를 확인해서 최종 답변 추출 방식을 확정한다.
4. `run_agent(golden_set[0]["inputs"])`부터 한 케이스씩 실행해 본다.
5. `evaluate_answer`, `evaluate_interrupts`, `evaluate_data`를 각각 따로 호출해서 결과를 확인한다.
6. `main()`에서 전체 Golden Set을 반복 실행한다.
7. 결과를 표 형태로 출력한다.

## 20. main에서 최종적으로 하고 싶은 구조

최종 목표는 대략 이런 흐름이다.

```python
def main():
    rows = []

    for case in golden_set:
        inputs = case["inputs"]
        reference = case["reference"]

        outputs = run_agent(inputs)

        answer_result = evaluate_answer(inputs, outputs, reference)
        interrupt_result = evaluate_interrupts(inputs, outputs, reference)
        data_result = evaluate_data(inputs, outputs, reference)

        rows.append({
            "case_id": case["case_id"],
            "answer": answer_result["score"],
            "interrupt": interrupt_result["score"],
            "data": data_result["score"],
        })

    print(rows)
```

나중에는 `pandas.DataFrame(rows)`로 표 출력하면 된다.

## 21. 헷갈렸던 점 정리

### case_id는 함수명이 아님

`case_id`는 그냥 케이스 이름이다.

함수처럼 호출되는 것이 아니라 결과표에서 구분자로 쓰인다.

### reference는 기대값

`reference`는 실제 결과와 비교할 기준이다.

그래서 `answer_criteria`, `expected_interrupts`, `expected_data`가 들어간다.

### expected_data 안의 변수명은 우리가 정하는 것

`changed`, `accounts`, `transactions_added` 같은 이름은 LangGraph 예약어가 아니다.

다만 한 번 정하면 평가 함수에서 같은 이름으로 읽어야 한다.

### 초기값은 initial_data.json에서 온다

각 평가 케이스는 독립적으로 실행되어야 한다.

그래서 매번 `initial_data.json`을 복사해서 같은 잔액에서 시작해야 한다.

## 22. 현재 판단

현재 방향은 맞다.

답변만 평가하는 것이 아니라,

```text
답변 평가 + interrupt 흐름 평가 + 데이터 상태 변화 평가
```

이 3가지를 같이 보는 구조가 이번 프로젝트에 맞다.

다만 `run_eval.py`는 아직 완성본이 아니라 실행 가능하게 다듬는 단계다.

다음 세션에서는 새 기능을 늘리기보다, 먼저 1개 케이스가 끝까지 돌아가게 만드는 것이 우선이다.
